# Build the sqlc fragment preprocessor nobody shipped

**No existing Go tool, library, sqlc plugin, or sqlc fork lets you define a SELECT list, WHERE predicate, JOIN block, or CTE once and splice it into several `-- name:` queries with sqlc-aware handling of annotations and parameters.** Exact-name searches on GitHub and pkg.go.dev for sqlc-fragments, sqlc-include, sqlc-macro, sqlc-preprocess and a dozen variants return nothing ([GitHub search](https://github.com/search?q=sqlc-fragments+in%3Aname&type=repositories)); what exists is an open proposal with zero code since 2023-04-30 ([issue #2244](https://github.com/sqlc-dev/sqlc/issues/2244)), two bespoke in-repo `text/template` pipelines, a 2025–2026 cluster of "dynamic query" plugins that add optional clauses inside one query but share nothing across queries, Bob's query generation (runtime mods on a generated base), and general templating libraries that know nothing about sqlc. The maintainer's own preferred answer, voiced on 2023-09-26, is "a templating system as a preprocessor step" rather than new `sqlc.*` syntax ([maintainer comment](https://github.com/sqlc-dev/sqlc/issues/2244#issuecomment-1735879805)), and nobody built it. The design that fits every constraint is a **generate-time pre-expander**: a dependency-free Go library that reads fragment definitions and query sources written as valid SQL with comment directives, splices fragment text at byte offsets, writes expanded `.sql` files into a build directory that `sqlc.yaml` points at, keeps a source map to rewrite sqlc's `file:line:col` diagnostics, and drives a pinned sqlc through `go tool`. This is forced rather than chosen, because sqlc's pipeline has no pre-parse hook and plugins run only after compilation, so the `.sql` files are the only seam. Expanding before sqlc types the whole query means fragments inherit sqlc's inference per use site, `sqlc.embed` and `sqlc.narg` work inside them (they cannot inside a VIEW), and the expanded SQL becomes a Go `const` with zero runtime cost and a stable byte sequence that pgx's statement cache keys on. The cross-engine rules are few: only named macros inside fragments, `sqlc.arg` rather than `@name` for MySQL, awareness that MySQL emits one `?` per occurrence while PostgreSQL and SQLite dedupe by name, and canonical single-line macro spelling. Build it in four phases (text expander, diagnostics and CI, parser-backed validation, Go-side plugin) and hedge the two real risks: sqlc's `main` branch is replacing every parser, and comment-based directives die under any AST-printing formatter.

## Nothing published shares SQL text across sqlc queries, and the gap has been open since 2019

sqlc ships exactly four macros, `sqlc.arg`, `sqlc.narg`, `sqlc.slice` and `sqlc.embed`, and none of them shares SQL text; `embed` "reuses existing model structs across queries", meaning generated Go structs for a whole table's columns inside one query ([Macros reference](https://docs.sqlc.dev/en/latest/reference/macros.html)). Every `-- name:` block compiles independently, so pasting the same CTE or column list into five queries is legal and simply compiles five times, producing five distinct `...Row` structs even when identical, which is the pain the open `:type` annotation PR targets ([PR #4630](https://github.com/sqlc-dev/sqlc/pull/4630)) and that "Override query return type" has carried **32 reactions since 2020** without resolution ([#781](https://github.com/sqlc-dev/sqlc/issues/781)). The only sanctioned reuse unit is a database VIEW: sqlc registers it as a catalog table whose columns are computed from the view's SELECT ([catalog/view.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/catalog/view.go)), which yields one shared Go type but costs a migration, flattens every LEFT-JOIN column to nullable, and cannot carry macros because the schema path has no rewrite step; the community's summary is "you cannot use things such as sqlc.embed in a view" ([#2244](https://github.com/sqlc-dev/sqlc/issues/2244)), and SQL functions are "much heavier... A function requires a migration, and mutating that function requires a REPLACE" ([#2244 comment](https://github.com/sqlc-dev/sqlc/issues/2244#issuecomment-2455623798)).

The request predates most of sqlc. Kyle Conroy's own 2019 issue "Query templates" asked how to "share a set of select expressions across queries", observed "There isn't a way to do this in the SQL standard", and closed in 2021 with "I haven't made any progress on this design" ([#112](https://github.com/sqlc-dev/sqlc/issues/112)). Three open successors carry no code: **#2244** proposes `-- name: WorkspaceCheck :fragment` plus `sqlc.fragment(WorkspaceCheck)` (open since 2023-04-30, 12 comments) ([#2244](https://github.com/sqlc-dev/sqlc/issues/2244)); **#2491** proposes `sqlc.view(book_with_author)` expanded at generation time "and never committing them to postgres" (open since 2023-07-21, zero comments) ([#2491](https://github.com/sqlc-dev/sqlc/issues/2491)); **#3410** asks to share one WHERE block between a list query and its COUNT (open, zero comments) ([#3410](https://github.com/sqlc-dev/sqlc/issues/3410)). The adjacent "dynamic queries" lineage is the project's most-upvoted request, **124 upvotes on discussion #364 since 2020** and 54 reactions on its issue twin ([D#364](https://github.com/sqlc-dev/sqlc/discussions/364), [#3414](https://github.com/sqlc-dev/sqlc/issues/3414)), yet every implementation PR before 2026 closed unmerged; the last maintainer verdict on one, in August 2025, was "I don't think this exact syntax is what we're going to adopt... please start a discussion first so that you don't implement a full feature I end up not merging" ([PR #4005](https://github.com/sqlc-dev/sqlc/pull/4005)). The one live prototype, compile-time `sqlc.switch` branches, has had no review since 2026-06-12 ([PR #4485](https://github.com/sqlc-dev/sqlc/pull/4485)), and the 2026 roadmap names database-only analysis, a Go API and ClickHouse, with no fragments and no dynamic queries ([D#4204](https://github.com/sqlc-dev/sqlc/discussions/4204)).

The third-party landscape sorts into four groups, none of which closes the gap:

kent is the closest working precedent and shows both why the approach works and what is missing. Its `queries.sql.tmpl` defines `{{define "taskSessionProjectionJoins"}}` and sibling partials shared by several `-- name:` queries, renders them to `queries.sql`, runs `sqlc generate` through `os/exec`, and deletes the rendered file in a `defer` ([queries.sql.tmpl](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querysrc/queries.sql.tmpl), [querygen/main.go](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querygen/main.go)); sqlc's errors therefore cite a file that no longer exists, parameters are passed into partials as raw template strings, and the sources are no longer SQL. That last cost is the recurring objection: Coder evaluated "SQLc + Go templates" in 2023 and instead moved its dynamic and join queries to sqlx plus Go templates, citing weaker SQL highlighting ([coder #6426](https://github.com/coder/coder/issues/6426)), and the same engineer told the sqlc tracker "you'd lose your source code being valid SQL. Right now that is a huge upside to SQLc" ([#2244](https://github.com/sqlc-dev/sqlc/issues/2244)). The dynamic-query cluster has production use (vtuanjs: "running in production at my company for about four months" ([D#364 comment](https://github.com/sqlc-dev/sqlc/discussions/364#discussioncomment-17210442))) and has learned useful sqlc facts the hard way, such as "sqlc treats a block comment starting at column zero as standalone ... and drops the whole line from Query.text" and "Keep the select list static" ([mpyw README](https://github.com/mpyw/sqlc-gen-go-dynamic)), but it answers dynamism, not deduplication. Bob is the only generator that, like sqlc, parses hand-written `.sql` query files and type-checks them against a schema; since v0.46.0 (2026-06-11) a generated query "can also be used as a QueryMod" and extended with `With(sm.Where(...))` ([Bob docs](https://bob.stephenafamo.com/docs/code-generation/queries), [CHANGELOG](https://github.com/stephenafamo/bob/blob/main/CHANGELOG.md)), but the reuse lives in Go after generation; a shared predicate is still duplicated in every `.sql` file. The one tool literally built for "fragments and partials for .sql files", dimfeld/sqlweld, is a Rust CLI for sqlx with **4 stars and no commit since 2023-12-28** ([sqlweld](https://github.com/dimfeld/sqlweld)).

Users describe the cost precisely. Brandur, with 700 queries in 101 files, calls the lack of "any kind of mechanism for putting dynamic code into queries" sqlc's "achilles heel" and copy/pastes CASE-flag blocks "as needed" ([brandur.org](https://brandur.org/fragments/sqlc-2024)); one tracker participant maintains list, count and sum variants with ">10 where conditions" by hand ([#2244](https://github.com/sqlc-dev/sqlc/issues/2244)); another keeps two copies of a query that differ only by `FOR UPDATE` ([D#364 comment](https://github.com/sqlc-dev/sqlc/discussions/364#discussioncomment-16447398)); a Hacker News commenter finds the omission "absolutely baffling" because "Composition of query fragments is, like, one of the main reasons you use a query builder" ([HN](https://news.ycombinator.com/item?id=41495664)). The community's standing advice, sqlc for static queries plus Squirrel or jet for dynamic ones ([Bytebase](https://www.bytebase.com/blog/golang-orm-query-builder/)), addresses dynamism rather than duplication and brings "2 different ways of handling SQL code in the same code base" ([D#364](https://github.com/sqlc-dev/sqlc/discussions/364)).

## sqlc's pipeline has no hook, so the `.sql` files are the only seam

`sqlc generate` is a fixed, hook-free sequence: load and validate config, then for every SQL block and output pair, in parallel up to `GOMAXPROCS`, glob the schema paths, parse DDL into a catalog, glob the query paths, parse each file whole, and per statement extract the `-- name:` line, validate macros, rewrite parameters and embeds, infer types, expand `*`, splice the text edits, build a `GenerateRequest`, and hand it to the built-in Go generator or a plugin, whose returned files are written under `out` ([generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go), [process.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/process.go), [compile.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/compile.go)). Nothing sits between `os.ReadFile` and the engine parser. Plugins are invoked by `ProcessResult` only after `parse()` has returned, can return nothing but files, and WASM plugins "do not have access to the network, filesystem, or environment variables" ([generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go), [plugins guide](https://docs.sqlc.dev/en/latest/guides/plugins.html)); they receive compiled `Query.text` with macros already rewritten and never see raw SQL or the AST ([codegen.proto](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/protos/plugin/codegen.proto), [shim.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/shim.go)). `sqlc vet` evaluates CEL over the same compiled text and only reports ([vet.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/vet.go)). The leverage points, in descending order, are therefore the files named by `queries:` and `schema:`, in-process invocation through `pkg/cli.Run`, a post-compile plugin for Go-side helpers, vet rules as a gate, and the config's top-level `options` map as a carrier.

The input side is friendlier than the docs suggest. `queries` accepts a file, a directory, or a list; directories are listed one level deep with `os.ReadDir`, entries containing `*?[]` go through `filepath.Glob` (since v1.24.0), and only lowercase `.sql` files that are not hidden and not down-migrations are kept, all resolved relative to the config file's directory ([sqlpath/read.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/sqlpath/read.go), [PR #2955](https://github.com/sqlc-dev/sqlc/pull/2955)). Pointing `queries: gen/sql` at a build directory is fully supported, and nothing in the documentation discourages generated input ([Configuration](https://docs.sqlc.dev/en/latest/reference/config.html)). The v2 config is parsed with `KnownFields(true)`, so unknown keys fail, but the top-level `options` map keyed by plugin name is never checked against declared plugins, which makes `options: { sqlcshare: {...} }` the one free slot for tool settings inside `sqlc.yaml` ([v_two.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/config/v_two.go), [config.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/config/config.go)). Output files are only ever written, never pruned ([cmd.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/cmd.go)), so a tool that renames generated query files must clean up after itself.

The query-file contract is strict and fully observable. A statement's raw text includes the comments preceding it, and `ParseQueryNameAndType` scans for a line that is exactly `-- name: Name :cmd` split on single spaces (also `/* name: ... */`, and `# name:` for MySQL); three tokens is "missing query type", any other count is "invalid query comment", and a statement with no match is silently skipped ([meta.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/metadata/meta.go)). Full-line comments other than the name line become `Query.comments`, which the Go generator renders as `//` doc comments on the method and passes to plugins, and any token in them starting with `@` is parsed as a flag (`@param`, `@sqlc-vet-disable`); inline and trailing comments, and multi-line `/* */` blocks, stay inside the query text ([source/code.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/source/code.go), [meta.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/metadata/meta.go)). Errors print as `relative/path.sql:line:col: message` with line and column computed from the byte offset in the file sqlc actually read, so a generated file is what gets cited ([multierr/errors.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/multierr/errors.go)); PostgreSQL and MySQL syntax errors carry positions, SQLite's ANTLR listener keeps only the message ([sqlite/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/sqlite/parse.go)).

Macro handling is text splicing driven by the AST, which is the single most useful fact for the design. `validate.SqlcFunctions` admits only `arg`, `narg`, `slice` and `embed` with one constant or column-reference argument ([param_style.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/validate/param_style.go)); mixing `$1` with `?` is an error and `$n` numbers must be contiguous from 1 ([param_ref.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/validate/param_ref.go)); `rewrite.NamedParameters` replaces each macro in the AST with a numbered `ParamRef` and records a `source.Edit` against the original text, and the code explicitly "assumes that sqlc.arg(name) / sqlc.narg(name) is on a single line with no extraneous spaces" ([rewrite/parameters.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/parameters.go)). Numbering comes from `ParamSet.Add`, where `hasNamedSupport = engine != mysql`: PostgreSQL and SQLite return the first number for a repeated name, MySQL allocates a fresh `?` per occurrence ([param_set.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/param_set.go)). The `@name` shorthand is detected on PostgreSQL as an `A_Expr` with operator `@` and on SQLite after the sigil is stripped, but MySQL converts it to a user variable that is never detected ([named/CLAUDE.md](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/CLAUDE.md), [sqlite/convert.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/sqlite/convert.go)); the docs confirm "@ ... is not supported in MySQL" and that "There is no nullable equivalent of the @ syntax" ([Named parameters](https://docs.sqlc.dev/en/latest/howto/named_parameters.html)). `sqlc.slice` becomes `ANY($1::type[])` on PostgreSQL but `/*SLICE:name*/?` inside `IN (...)` on MySQL and SQLite, expanded by generated Go at runtime, which is why it "isn't compatible with the emit_prepared_queries configuration option" ([Retrieving rows](https://docs.sqlc.dev/en/latest/howto/select.html)); SQLite queries mixing a slice with other parameters have been broken since 2023 ([#2452](https://github.com/sqlc-dev/sqlc/issues/2452)). `rewrite.Embeds` turns `sqlc.embed(t)` into `t.*`, and `expand` turns every star into an explicit, dialect-quoted column list on the final assembled query, with backticks on MySQL ([embeds.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/embeds.go), [expand.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/expand.go)). Because a pre-expander runs before all of this, a fragment may contain anything a hand-written query may: `*`, `sqlc.embed`, `sqlc.narg`, casts, CTE bodies.

Typing explains why fragments should not carry their own types. Parameter types are resolved per query in `resolveCatalogRefs` from the column each placeholder is compared with, including inferred nullability ([resolve.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/resolve.go)); CTEs are registered per query in `QueryCatalog.ctes` and looked up before real tables ([query_catalog.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/query_catalog.go)); nullability follows a small rule set with LEFT, RIGHT and FULL join demotion ([output_columns.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/output_columns.go)). A WHERE fragment used against two tables therefore legitimately gets two parameter types, which is the objection raised inside #2244 and the reason a tool must not synthesize one shared `FragmentParams` struct. The CTE resolver has open defects the expander inherits, most importantly `table alias "..." does not exist` when a CTE column is compared with `sqlc.arg` (10 reactions, workaround: cast the argument, fix PR unreviewed since 2024) ([#3585](https://github.com/sqlc-dev/sqlc/issues/3585)), and `sqlc.embed` cannot target a CTE at all ([#3128](https://github.com/sqlc-dev/sqlc/issues/3128)).

Importability settles the integration mode. Only `github.com/sqlc-dev/sqlc/pkg/cli` is public, exposing `Run(args []string) int`, which wraps `internal/cmd.Do(args, os.Stdin, os.Stdout, os.Stderr)` ([pkg/cli/cli.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/pkg/cli/cli.go)); every parser, compiler and codegen package is under `internal/`, which the Go toolchain refuses to import ([Go internal directories](https://pkg.go.dev/cmd/go#hdr-Internal_Directories)). The module requires **Go 1.26** and carries pg_query_go v6.2.2 (cgo) with the go-pgquery WASM fallback, the TiDB parser, antlr4-go, wazero and cel-go ([go.mod @ v1.31.1](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/go.mod)). `sqlc parse --dialect` (v1.31.0) prints sqlc's AST as JSON with no config or database ([parse docs](https://docs.sqlc.dev/en/latest/howto/parse.html)), and `sqlc analyze` and `sqlc fmt` exist on `main` only ([analyze docs](https://docs.sqlc.dev/en/latest/howto/analyze.html), [fmt docs](https://docs.sqlc.dev/en/latest/howto/fmt.html)). sqlc's own AST formatter defines `Format` for **70 of 306 node files**, so even a vendored copy could not round-trip arbitrary queries ([ast/print.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/ast/print.go)); text splicing, which is what sqlc itself does, is the proven path.

The target is moving. On `main`, PR #4537 (merged 2026-07-31) moved macro handling into a new `internal/sql/preprocess` package that rewrites `sqlc.arg` to `$1`, `?` or `?1` before parsing ([PR #4537](https://github.com/sqlc-dev/sqlc/pull/4537)); `go.mod` on `main` lists oliphant, marino, meyer, zetajones, darkwing, teesql and doubleclick and no longer pg_query_go or the TiDB parser ([go.mod @ main](https://github.com/sqlc-dev/sqlc/blob/main/go.mod)); and the engine-plugin PR was declined with "I'm currently rebuilding the analysis framework. It's going to look substantially different" ([PR #4247](https://github.com/sqlc-dev/sqlc/pull/4247)). The project is effectively single-maintainer (kyleconroy 861 commits, andrewmbenton 95 and last active 2025-08) with two to three releases a year and none since 2026-04-22 ([contributors](https://github.com/sqlc-dev/sqlc/graphs/contributors), [releases](https://github.com/sqlc-dev/sqlc/releases)). A tool that depends only on the `.sql` contract and the three stable engines will age best.

## Precedents settle three design choices: expand before typing, splice text, keep parameters named

**Expand before typing.** Every statically typed SQL tool surveyed types a whole query and none types a fragment on its own. PgTyped and Prisma TypedSQL infer from a live database per standalone query and document no composition ([PgTyped](https://pgtyped.dev/docs/sql-file), [Prisma TypedSQL](https://www.prisma.io/docs/orm/prisma-client/using-raw-sql/typedsql)); sqlx's `query!` insists "The query must be a string literal, or concatenation of string literals" because anything else "cannot be introspected" ([sqlx](https://docs.rs/sqlx/latest/sqlx/macro.query.html)); Ecto's `fragment` refuses interpolated SQL as its first argument "to prevent SQL injection attacks" ([ecto builder.ex](https://github.com/elixir-ecto/ecto/blob/master/lib/ecto/query/builder.ex)). Diesel does compose typed fragments in Rust, but "a boxed expression can only be used with exactly the from clause given" ([Diesel](https://diesel.rs/guides/composing-applications.html)), the same per-site typing constraint that sqlc's `resolveCatalogRefs` imposes. A Go pre-expander sidesteps the literal-only rule by producing literal SQL before the typer runs, which is also precisely what the sqlc maintainer sketched.

**Splice text at offsets; never deparse.** MyBatis is the canonical load-time include: `<sql id>` fragments spliced by `<include refid>` with `<property>` values substituted into `${}` placeholders, nestable, with the explicit warning that `${}` "won't modify or escape the string" ([MyBatis](https://mybatis.org/mybatis-3/sqlmap-xml.html)). dbt compiles Jinja macros to plain SQL under `target/compiled/` and inlines ephemeral models into dependents as CTEs prefixed `__dbt__cte__`, which is #2491's `sqlc.view` idea already in production elsewhere ([dbt macros](https://docs.getdbt.com/docs/build/jinja-macros), [dbt materializations](https://docs.getdbt.com/docs/build/materializations)). On the parser side, no Go SQL parser keeps comments in its tree: libpg_query exposes comments only through the scanner as `C_COMMENT` tokens with byte offsets ([libpg_query README](https://github.com/pganalyze/libpg_query/blob/17-latest/README.md)), Vitess keeps only leading `ParsedComments` ([vitess ast.go](https://github.com/vitessio/vitess/blob/main/go/vt/sqlparser/ast.go)), and TiDB's `Restore` re-emits only TiDB special comments ([parser/format](https://pkg.go.dev/github.com/pingcap/tidb/pkg/parser/format)). A parse-then-deparse round trip would therefore destroy the `-- name:` headers and macro comments sqlc depends on. The parsers worth knowing for validation are pg_query_go v6.2.5 (cgo, BSD-3, first build "up to 3 minutes") ([pg_query_go](https://github.com/pganalyze/pg_query_go)); wasilibs/go-pgquery, a pure-Go drop-in via wazero that is "about 4-5x slower than cgo" at roughly 25 µs versus 6.6 µs per simple SELECT ([go-pgquery README](https://github.com/wasilibs/go-pgquery/blob/main/README.md)); sqlc-dev/oliphant, a hand-written pure-Go port claiming "same exported functions, same generated protobuf types ... same fingerprints" and already imported by sqlc `main` ([oliphant](https://github.com/sqlc-dev/oliphant), [sqlc main parse.go](https://github.com/sqlc-dev/sqlc/blob/main/internal/engine/postgresql/parse.go)); for MySQL the TiDB parser or sqlc's recursive-descent fork marino ([marino](https://github.com/sqlc-dev/marino)); for SQLite sqlc's new meyer or rqlite/sql, whose AST has `String()` on 83 node types ([meyer](https://github.com/sqlc-dev/meyer), [rqlite/sql ast.go](https://github.com/rqlite/sql/blob/master/ast.go)). jOOQ's plain-SQL templating supplies the minimum lexical rule for a splicer: a mini parser that ignores placeholders inside string literals, quoted names and comments ([jOOQ templating](https://www.jooq.org/doc/latest/manual/sql-building/plain-sql-templating/)), which a scanner provides without a full parse.

**Keep parameters named.** HugSQL, the only member of the `-- :name` file family with real fragments, splices snippets at runtime by joining SQL strings with a space and concatenating parameter tails in textual order ([HugSQL snippets](https://www.hugsql.org/using-hugsql/composability/snippets), [parameters.clj](https://github.com/layerware/hugsql/blob/master/hugsql-core/src/hugsql/parameters.clj)); Kysely and Drizzle number placeholders in emission order per dialect, `$N` for Postgres and `?` for MySQL and SQLite ([default-query-compiler.ts](https://github.com/kysely-org/kysely/blob/master/src/query-compiler/default-query-compiler.ts), [Drizzle sql](https://orm.drizzle.team/docs/sql)). With named `sqlc.arg()` macros none of that machinery is needed, because sqlc numbers placeholders after expansion and dedupes repeated names on PostgreSQL and SQLite. Doma's SQL templates show how to keep files executable: a directive comment is followed by a fallback token that runs unchanged outside the template engine, as in `/*%expand "alias"*/*` ([Doma](https://docs.domaframework.org/en/latest/sql/)), the same trick sqlc's own `-- name:` header uses. dbt's warnings that "it's easy to fall down a rabbit hole when it comes to whitespace control" and that macros "can make your models harder for other users to interpret... even if it means repeating some lines of SQL" ([dbt macros](https://docs.getdbt.com/docs/build/jinja-macros)) argue for a deliberately tiny directive language rather than embedding a general template engine. SQLDelight's grouped statements, one label over several statements sharing a parameter set ([SQLDelight grouping](https://sqldelight.github.io/sqldelight/latest/jvm_sqlite/grouping_statements/)), are the precedent for deriving list and count variants from one source later.

## The plan: a generate-time expander with valid-SQL sources and a source map

The architecture is a straight pipeline with one library at its core and no dependency on sqlc. Fragment files and query sources, both valid SQL, are loaded into a fragment library (name, identifier parameters, kind, raw body, position). An expander walks each query source with a comment- and string-aware scanner, resolves directives, substitutes identifier arguments, wraps the fragment body according to its kind, splices it at the directive's byte offsets, and records a source map. A writer emits `gen/sql/<same relative path>` deterministically and owns that directory. A runner invokes a pinned sqlc and pipes its stderr through the source map. An optional codegen plugin, later, consumes provenance comments. In Go terms that is `sqlcshare` (core, standard library only), `sqlcshare/lexer/{postgres,mysql,sqlite}` (optional scanners), `sqlcshare/runner`, and `cmd/sqlcshare`; the name is free, as are sqlc-fragments, sqlc-include, sqlc-macro and sqlc-preprocess ([GitHub search](https://github.com/search?q=sqlc-fragments+in%3Aname&type=repositories)).

### Syntax: comment directives with fallback text keep query files runnable

Fragment definitions use the `-- name:` shape sqlc users already know, with a kind instead of a command, and live in files that `sqlc.yaml` never lists. Use sites are block-comment directives in the Doma style; the text between a directive and its `/*%end*/` is a fallback that makes the source a complete, runnable statement for psql and the IDE, and is discarded on expansion. A directive without `/*%end*/` is replaced in place for authors who do not care about runnability.

```sql
-- fragments/authors.sql          (never referenced from sqlc.yaml)

-- fragment: author_cols(a) :columns
{a}.id, {a}.name, {a}.created_at;

-- fragment: visible_author(a) :where
{a}.deleted_at IS NULL AND {a}.org_id = sqlc.arg(org_id);

-- fragment: recent_orders :cte
SELECT o.* FROM orders o WHERE o.created_at > sqlc.narg(since)::timestamptz;

-- queries/authors.sql            (source; sqlc.yaml lists gen/sql instead)

-- name: ListAuthors :many
/*%with recent_orders*/
SELECT /*%columns author_cols(a)*/ a.* /*%end*/, count(r.id) AS orders
FROM authors a
LEFT JOIN recent_orders r ON r.author_id = a.id
WHERE /*%where visible_author(a)*/ TRUE /*%end*/
  AND a.name ILIKE sqlc.arg(pattern)
GROUP BY a.id;
```

The expander produces, under `gen/sql/queries/authors.sql`:

```sql
-- name: ListAuthors :many
-- sqlcshare: queries/authors.sql:3 (with recent_orders, columns author_cols, where visible_author)
WITH recent_orders AS (SELECT o.* FROM orders o WHERE o.created_at > sqlc.narg(since)::timestamptz)
SELECT a.id, a.name, a.created_at, count(r.id) AS orders
FROM authors a
LEFT JOIN recent_orders r ON r.author_id = a.id
WHERE (a.deleted_at IS NULL AND a.org_id = sqlc.arg(org_id))
  AND a.name ILIKE sqlc.arg(pattern)
GROUP BY a.id;
```

Four kinds cover the question's four cases and each has one wrapping rule. `:columns` and `:joins` splice verbatim. `:where` is always wrapped in parentheses, so a fragment containing `OR` cannot change the precedence of the enclosing predicate. `:cte` splices the body as `name AS (...)`: if the statement already begins with `WITH` or `WITH RECURSIVE` the clause is inserted after that keyword with a trailing comma, otherwise `WITH name AS (...)` is prepended; this is dbt's ephemeral inlining and #2491's `sqlc.view` in one rule. A fifth `:sql` kind is the unwrapped escape hatch. Fragment arguments are identifiers only, validated against `^[A-Za-z_][A-Za-z0-9_]*$` and substituted for `{a}` tokens, so the mechanism has none of MyBatis's `${}` injection surface; the same mechanism renames parameters when one fragment is used twice in a query, as in `sqlc.arg({p}since)` with `p=from_`. Fragments may include fragments, with cycle detection. The provenance line is deliberately a full-line comment: sqlc copies it into `Query.comments`, which the Go generator emits as a doc comment on the method and plugins receive, so generated Go says which source and fragments produced each query ([source/code.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/source/code.go)); it must not contain `@` tokens, which sqlc would parse as flags ([meta.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/metadata/meta.go)). Version 1 keeps fragment bodies as raw text because that needs no parser; if fragment files must themselves be executable, Phase 3's parsers enable an alternative definition form, a complete SELECT whose kind names the clause to extract, without changing the use-site syntax.

### Parameters and macros: one rule set, three engine profiles

Six rules make fragments behave identically on all three engines. First, fragments may use only the named macros `sqlc.arg`, `sqlc.narg` and `sqlc.slice`; positional `$N` and `?` inside a fragment are rejected, because sqlc requires contiguous numbering and forbids mixing styles ([param_ref.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/validate/param_ref.go)), and because named macros let sqlc number and dedupe after expansion, which removes the renumbering pass every runtime composer needs. Second, the expander normalizes `@name` in fragment bodies to `sqlc.arg(name)` in the output: the two are documented as equivalent and `@` has no nullable form ([Named parameters](https://docs.sqlc.dev/en/latest/howto/named_parameters.html)), and the rewrite is what makes a fragment portable to MySQL, where `@name` becomes a user variable ([named/CLAUDE.md](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/CLAUDE.md)). Third, macros are emitted in canonical single-line form, `sqlc.arg(name)` with no inner whitespace, because sqlc's text edit reconstructs the old string under exactly that assumption ([rewrite/parameters.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/parameters.go)). Fourth, a parameter name repeated across fragments collapses to one placeholder on PostgreSQL and SQLite but yields one `?` per occurrence on MySQL ([param_set.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/param_set.go)); fragment reuse makes repetition far more likely, so the tool's documentation should pin `query_parameter_limit` at its default, since a repeated `sqlc.narg` with a higher limit generates `name redeclared in this block` on MySQL in v1.30.0 ([#4191](https://github.com/sqlc-dev/sqlc/issues/4191)). Fifth, `sqlc.slice` is allowed but documented as incompatible with `emit_prepared_queries` and with other parameters on SQLite ([Retrieving rows](https://docs.sqlc.dev/en/latest/howto/select.html), [#2452](https://github.com/sqlc-dev/sqlc/issues/2452)). Sixth, `sqlc.embed` is allowed in `:columns` fragments, which is the headline advantage over views, with two caveats: embedding a LEFT-JOINed table still scans NULL rows into non-nullable fields, an open issue with 51 reactions ([#2348](https://github.com/sqlc-dev/sqlc/issues/2348)), and embedding a `:cte` fragment's name will not work because embed cannot target a CTE ([#3128](https://github.com/sqlc-dev/sqlc/issues/3128)). For `:cte` fragments on PostgreSQL, cast any `sqlc.arg` compared against a CTE column, the documented workaround for the alias-resolution bug ([#3585](https://github.com/sqlc-dev/sqlc/issues/3585)).

| Concern | PostgreSQL | MySQL | SQLite |
|---|---|---|---|
| Placeholder sqlc emits | `$n`, one per distinct name | `?`, one per occurrence | `?n`, one per distinct name ([param_set.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/param_set.go), [parameters.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/parameters.go)) |
| `@name` shorthand | supported | not supported, parsed as a user variable | supported ([Named parameters](https://docs.sqlc.dev/en/latest/howto/named_parameters.html)) |
| `sqlc.slice` | `ANY($1::type[])` | `IN (/*SLICE:name*/?)`, expanded at runtime | as MySQL; broken when mixed with other params ([select docs](https://docs.sqlc.dev/en/latest/howto/select.html), [#2452](https://github.com/sqlc-dev/sqlc/issues/2452)) |
| Syntax-error position | line and cursor from pg_query | line and column parsed from the TiDB message | message only, no position ([sqlite/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/sqlite/parse.go)) |
| Statement text extent | `StmtLocation`/`StmtLen` | `strings.Index(blob, stmt.Text())` | previous statement's stop plus 2, so inter-statement comments belong to the next statement ([postgresql/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/postgresql/parse.go)) |
| Star-expansion quoting | double quotes | backticks | double quotes, `jsonb` wrapped in `json()` ([expand.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/expand.go)) |
| Parser, v1.31.1 then `main` | pg_query_go v6.2.2 / go-pgquery, then oliphant | TiDB parser, then marino | ANTLR grammar, then meyer ([go.mod v1.31.1](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/go.mod), [go.mod main](https://github.com/sqlc-dev/sqlc/blob/main/go.mod)) |

### Library surface and invocation

The core package should read like `go/scanner` plus `go/printer` for this one job, with the engine as a value and the scanner as an interface so Phase 3 can plug in real lexers without changing callers.

```go
package sqlcshare

type Engine uint8 // PostgreSQL, MySQL, SQLite
type Kind uint8   // Columns, Where, Joins, CTE, Raw

type Fragment struct {
    Name   string
    Params []string // identifier arguments, e.g. ["a"]
    Kind   Kind
    Body   string   // raw text between the header and ';'
    Pos    Pos      // file, line, column of the header
}

type Library struct{ /* name -> *Fragment, insertion ordered */ }
func Load(fsys fs.FS, globs ...string) (*Library, error)

type Scanner interface { // comment-, string- and quoted-identifier-aware
    Next() (Token, bool)
}

type Expander struct {
    Engine  Engine
    Lib     *Library
    NewScan func([]byte) Scanner // nil selects the built-in scanner
}
func (e *Expander) Expand(name string, src []byte) (out []byte, sm *SourceMap, err error)

type SourceMap struct{ /* sorted segments: output line -> (file, line, column delta) */ }
func (m *SourceMap) Origin(line, col int) (Pos, bool)
func RewriteDiagnostics(r io.Reader, w io.Writer, maps map[string]*SourceMap) error
```

Invocation follows Go 1.24's tool directives: `go get -tool github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1` pins sqlc in `go.mod`, and `//go:generate go tool sqlcshare generate` runs the expander, which then execs `go tool sqlc generate -f sqlc.yaml` ([Go 1.24 release notes](https://go.dev/doc/go1.24)); sqlc's docs never mention `go:generate` or `go tool`, but the repo's `placeholder.go` exists precisely so the module can be pinned and run from `go.mod` ([placeholder.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/placeholder.go)). Exec rather than in-process is the default on purpose: `pkg/cli.Run` is hard-wired to `os.Stdout` and `os.Stderr` ([pkg/cli/cli.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/pkg/cli/cli.go)), so diagnostics cannot be captured and rewritten without redirecting process-level file descriptors, and importing sqlc drags in Go 1.26, cgo or the WASM parser, wazero and cel-go ([go.mod @ v1.31.1](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/go.mod)). Offer in-process mode behind a build tag for teams that want a single binary. Configuration lives either in `sqlcshare.yaml` or in the ignored `options: sqlcshare:` block of `sqlc.yaml`; the user sets `queries: gen/sql` and keeps `schema:` unchanged ([Configuration](https://docs.sqlc.dev/en/latest/reference/config.html)). CI runs `sqlcshare generate && sqlc diff` so drift in either layer fails the build ([cmd.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/cmd.go)). An optional enforcement gate uses `sqlc vet`: an inline marker the expander places inside each expanded statement survives into `query.sql`, because only full-line comments are stripped, so the CEL rule `!query.sql.contains("/* sqlcshare */")` flags a hand-written query that bypassed the expander ([vet docs](https://docs.sqlc.dev/en/latest/howto/vet.html), [source/code.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/source/code.go)); the marker ships inside the SQL constant, so make it opt-in.

### Diagnostics, determinism, and generator cost

sqlc cites the file it read, so the source map is the feature that separates a library from kent's script. The map is a sorted slice of segments keyed by output line; single-line fragments spliced inline keep the following text on the same line, multi-line bodies shift everything after them, and both cases are recorded at splice time. `RewriteDiagnostics` matches the `path.sql:line:col: message` shape sqlc prints relative to the config directory ([multierr/errors.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/multierr/errors.go), [generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go)) and replaces it with the source position; for SQLite, whose syntax errors carry no position, it falls back to the query name and the source span of that statement. The provenance comment is the belt to those braces: even without the wrapper, a developer reading `gen/sql` sees where each line came from. Output must be byte-deterministic for the same input: sqlc processes `os.ReadDir` and `filepath.Glob` results in lexical order ([sqlpath/read.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/sqlpath/read.go)), so the expander should emit files in the same order, never write timestamps, and delete the whole `gen/sql` tree before writing, since sqlc never prunes its own outputs ([cmd.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/cmd.go)). Generator cost is not a concern at any realistic scale: text splicing is linear in input size, Brandur's 700 queries across 101 files is a reasonable upper bound ([brandur.org](https://brandur.org/fragments/sqlc-2024)), and even full-parser validation runs at roughly 25 to 190 µs per statement under the WASM PostgreSQL parser and 4 to 5 times faster under cgo ([go-pgquery README](https://github.com/wasilibs/go-pgquery/blob/main/README.md)), well under a second for the whole corpus. Hashing inputs to skip sqlc when nothing changed is the only optimization worth building, because sqlc itself re-parses every schema file on every run ([compile.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/compile.go)).

### Runtime cost is zero and statement caches stay warm

Pre-expansion inherits sqlc's runtime profile for free. The Go generator emits each query as a `const` string with the `-- name:` line re-synthesized ([result.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/codegen/golang/result.go), [queryCode.tmpl](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/codegen/golang/templates/stdlib/queryCode.tmpl)), and Go evaluates constant expressions at compile time ([Go spec](https://go.dev/ref/spec)), so a fragment-expanded query costs no allocation and no concatenation per call. Stable bytes matter beyond CPU: pgx's default `QueryExecModeCacheStatement` looks statements up by SQL text (`c.statementCache.Get(sql)`) and names them `"stmtcache_" + hex(sha256(sql)[0:24])`, "stable for sql across multiple connections and program executions", with a default capacity of **512** ([pgx conn.go](https://github.com/jackc/pgx/blob/master/conn.go), [stmtcache.go](https://github.com/jackc/pgx/blob/master/internal/stmtcache/stmtcache.go), [pgx docs](https://pkg.go.dev/github.com/jackc/pgx/v5)). One expanded query is therefore exactly one cache entry and one server-side plan per connection, whereas runtime-assembled fragments with any whitespace or ordering variance multiply entries. The measured envelope confirms the target: in the only multi-library dataset (2024-10-15, GitHub Actions runner), a single-row read costs sqlc 148,618 ns and 19 allocations against raw pgx's 148,944 ns and 18, while jet takes 194,693 ns and 273 allocations and sq 175,209 ns and 135 ([results.md](https://github.com/efectn/go-orm-benchmarks/blob/master/results.md)); builder-only string assembly adds 1 to 3.5 µs and 25 to 87 allocations per simple SELECT in the Bob author's 2023 benchmark ([go-sql-builder-benchmarks](https://github.com/stephenafamo/go-sql-builder-benchmarks)). The planner argument is the deeper one. The maintainer-endorsed optional-filter patterns, `(col = sqlc.narg('x') OR sqlc.narg('x') IS NULL)` and `CASE WHEN @flag::bool THEN ... ELSE TRUE END`, are acknowledged by the maintainers to "perform poorly in production" and to work "only ... for a small number of parameters" ([D#580](https://github.com/sqlc-dev/sqlc/discussions/580#discussioncomment-55097), [D#364](https://github.com/sqlc-dev/sqlc/discussions/364#discussioncomment-7004672)), and users report the planner "has to prepare for the worst case... no indexes will be used" ([D#364](https://github.com/sqlc-dev/sqlc/discussions/364)). Fragment reuse removes the reason people reach for those patterns: the shared predicate is written once and every expanded query stays static, which keeps the planner's view static. Binary size grows only by the duplicated fragment text per use site, kilobytes, and no parser is linked into the application because expansion happens at `go generate` time.

### Phases and exit criteria

| Phase | Deliverable | Exit criterion |
|---|---|---|
| 0, spike | Hand-expand a kent-shaped example on all three engines; capture how sqlc reports a bad column inside a spliced fragment; verify how generated Go binds a name repeated across fragments on MySQL | Written notes on the diagnostics shape per engine and on the MySQL repeated-name behaviour |
| 1, expander | `Load`, `Expand`, writer, `cmd/sqlcshare generate`, `go:generate` wiring, deterministic output, owned `gen/sql`, golden tests per engine | Identical bytes on repeated runs; `sqlc generate` succeeds on the expanded corpus for PostgreSQL, MySQL and SQLite |
| 2, diagnostics and CI | `SourceMap`, `RewriteDiagnostics`, exec runner, `diff` mode, optional vet marker, `options: sqlcshare` config | Every sqlc error on a fragment points at the fragment file and line; CI fails on drift |
| 3, validation | Pluggable scanners (libpg_query scanner via go-pgquery or oliphant, TiDB or marino lexer, meyer or rqlite/sql); check fragment kind against slot, reject placeholders inside strings and comments, optional `sqlc parse` cross-check of expanded output | Malformed splices are rejected before sqlc runs, with source positions |
| 4, Go side | Optional codegen plugin reading provenance comments to emit shared parameter structs where types provably agree; derived variants (`Count` from a list query by replacing the `:columns` slot and dropping ORDER BY and LIMIT) | Shared structs compile for queries whose inferred parameter types match; count variants solve #3410 without hand copies |

Phase 0 exists because two facts are unverified in the research: how the Go generator passes a MySQL argument that appears at several `?` positions, and the exact shape of multi-fragment diagnostics. Phase 1 deliberately ships with no SQL parser, so the core has no dependencies and no cgo; the built-in scanner only needs to recognize `--` and `/* */` comments, single- and double-quoted strings and dollar quoting, the same set sqlc's own `sqlfile.Split` honours ([sqlfile/split.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/sqlfile/split.go)), plus backticks for MySQL. Phase 3 is where engine parsers earn their cost, and the choice should track sqlc: oliphant, marino and meyer are what sqlc `main` consumes ([go.mod @ main](https://github.com/sqlc-dev/sqlc/blob/main/go.mod)), so expansions and sqlc see identical trees, while `sqlc parse --dialect` offers an engine-neutral cross-check from the installed binary ([parse docs](https://docs.sqlc.dev/en/latest/howto/parse.html)). Phase 4's plugin is the only place sqlc's plugin protocol helps: `Query.comments` carries the provenance line into the `GenerateRequest`, and a plugin generated from sqlc's current `codegen.proto` rather than the stale plugin-sdk-go (last published 2023-11-02) can group queries by fragment ([codegen.proto](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/protos/plugin/codegen.proto), [plugin-sdk-go versions](https://pkg.go.dev/github.com/sqlc-dev/plugin-sdk-go?tab=versions)).

### Risks and how to hedge them

The largest risk is sqlc's own churn. Every parser is being replaced on `main`, a preprocess pass now rewrites macros before parsing, and `sqlc fmt` on `main` "rewrites the query files referenced by your sqlc configuration into a canonical format" by printing from the AST ([fmt docs](https://docs.sqlc.dev/en/latest/howto/fmt.html)); because no parser keeps comments in its tree, running that formatter over directive-bearing sources would erase the directives, so sources must never appear in `queries:` and the tool should refuse to run if they do. Depending only on the `.sql` contract and the macro set, which has not changed since v1.18.0 added `embed` and `slice` ([v1.18.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.18.0)), is the hedge; the roadmap's promised "first-class Go API, similar to how esbuild does it" ([D#4204](https://github.com/sqlc-dev/sqlc/discussions/4204)) should be absorbed behind the runner interface when it ships. The second risk is adoption friction over source validity, which the fallback-text syntax addresses at the price of verbosity; a terse no-fallback form keeps the choice with the author. Third, inherited sqlc defects will surface more often because fragments concentrate CTEs and repeated parameters: the CTE alias bug ([#3585](https://github.com/sqlc-dev/sqlc/issues/3585)), SQLite slice mixing ([#2452](https://github.com/sqlc-dev/sqlc/issues/2452)) and the MySQL repeated-`narg` codegen bug ([#4191](https://github.com/sqlc-dev/sqlc/issues/4191)) all need entries in the tool's documentation, and SQLite's positionless syntax errors need the name-based fallback. Fourth, scope creep toward dynamic queries is the classic failure mode here; the tool should state that optional clauses are a non-goal and point at vtuanjs's plugin, go-sqletch or PR #4485 for that half of the problem, with which it composes because expansion runs first. Fifth, fragment parameter types differ per use site by design; any shared-struct feature must prove type equality from sqlc's output rather than assume it, or it recreates the problem Diesel documents and #2244 raised.

## Conclusion

The research reframes the question: the absence of a fragment tool is not an unsolved technical problem but an unfilled niche that sqlc's own architecture has pointed at since 2023. Everything a pre-expander needs is already true of sqlc: it reads whatever `.sql` files it is told to, it numbers and dedupes named parameters after the fact, it types every query per use site, it tolerates comments anywhere, and it emits constants. The ecosystem's energy went into dynamic queries, which fight sqlc's compile-one-query model, while cross-query deduplication, which does not, was left to two private template scripts. A library that stays text-based, keeps sources valid SQL through fallback directives, and treats sqlc as a pinned black box with a source map in front of it would be the first general answer to a request that spans #112, #2244, #2491 and #3410, and it would compose with, rather than compete against, the dynamic-query plugins.

The non-obvious implication for an engineer who prioritizes performance is that the fastest fragment system is the one with no runtime at all. The runtime builders in the Go ecosystem pay microseconds and dozens of allocations per query and fragment the prepared-statement cache; a generate-time expander pays nothing and leaves one stable statement per query. That is also why the design should resist growing an AST round-trip or a template engine: the value is in the thin layer between an author's intent and sqlc's unchanged pipeline, and the moment the tool deparses or interpolates it inherits the comment-loss and injection problems every precedent warns about.
