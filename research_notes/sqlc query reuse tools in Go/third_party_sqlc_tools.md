# Third-party sqlc query re-use tools in Go (state as of 2026-10-19)

Scope note: everything below was verified on 2026-10-19 against the GitHub REST/GraphQL API (authenticated `gh`), GitHub code search, pkg.go.dev, and fetched web pages. Star counts, created/pushed dates and release tags are API values from that day. Items I could not open are marked UNVERIFIED. "Text-based" means the tool manipulates SQL as strings/templates; "SQL-AST-aware" means it parses the SQL. Reddit could not be fetched (HTTP 403 on reddit.com and on a redlib mirror), and Gophers Slack/Discord are not searchable from here; both are recorded under Gaps.

## Core question: does a Go tool already exist that lets sqlc users share and re-use SQL query fragments across queries?

### Takeaway
No. As of 2026-10-19 there is no published Go library, CLI, sqlc plugin or sqlc fork that lets a user define a SQL fragment once (a WHERE predicate, join block, column list, CTE) and splice it into several `-- name:` queries with sqlc-aware handling of annotations, `sqlc.*` macros and parameters. What exists instead is (a) one open 2023 proposal in the sqlc tracker with zero prototype code, (b) two bespoke, in-repo `text/template` pipelines in application repositories, (c) a cluster of "dynamic query" tools that add optional clauses *within* one query but do not share SQL *across* queries, and (d) general-purpose SQL templating libraries that are not sqlc-aware.

### Cited Findings
- The sqlc tracker's "Feature proposal: Query Fragments" (issue #2244) proposes `-- name: WorkspaceCheck :fragment` plus `sqlc.fragment(WorkspaceCheck)` with an embedded `WorkspaceCheckFragmentParams` struct; it has been OPEN since 2023-04-30 with 12 comments and 8 reactions, and no linked branch or PR — [sqlc issue #2244](https://github.com/sqlc-dev/sqlc/issues/2244)
- In that thread the maintainer wrote on 2023-09-26: "Instead of adding a new `sqlc.xxx` function, I've been thinking about adopting the a templating system as a preprocessor step. Jinja2 supports macro definitions, which should solve your issue without us introducing any new special syntax." — [kyleconroy, issue #2244](https://github.com/sqlc-dev/sqlc/issues/2244)
- Nothing followed that idea: a GraphQL search of sqlc issues/PRs for "jinja" returns only 8 docs dependency-bump PRs, zero discussions, and a code search hits only `docs/reference/changelog.md` — [GitHub search, repo:sqlc-dev/sqlc jinja](https://github.com/sqlc-dev/sqlc/issues?q=jinja)
- Exact-name repository searches on GitHub for sqlc-fragments, sqlc-fragment, sqlc-tpl, sqlc-include, sqlc-macro, sqlc-macros, sqlc-partials, sqlc-partial, sqlc-preprocess, sqlc-preprocessor, sqlc-compose, sqlc-dynamic, sqlc-gen-go-templates, sqlc-views, sqlc-cte, sqlc-builder, sqlcgen return no repository with that exact name (see the verification table below) — [GitHub repository search](https://github.com/search?q=sqlc-fragments+in%3Aname&type=repositories)
- The only application repositories found on GitHub that render hand-written sqlc query files from Go templates are respawn-llc/kent (uses `{{define}}` partials such as `taskSessionProjectionJoins` shared by several `-- name:` queries, rendered into `server/metadata/queries.sql`, then `sqlc generate` is executed and the rendered file deleted) and lsdch/BiOME (renders N ORDER BY variants of one query from a YAML list) — [kent querysrc/queries.sql.tmpl](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querysrc/queries.sql.tmpl); [kent querygen/main.go](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querygen/main.go); [BiOME internal/sqlcgen/generator.go](https://github.com/lsdch/BiOME/blob/HEAD/server/db/internal/sqlcgen/generator.go)
- The closest "fragments and partials for .sql files" tool is dimfeld/sqlweld, a Rust CLI (Tera templates, `.partial.sql.tera` and `.macros.sql.tera`), whose README targets Rust sqlx, never mentions sqlc, has 4 stars and was last pushed 2023-12-28 — [dimfeld/sqlweld](https://github.com/dimfeld/sqlweld)
- The newest adjacent tool, moznion/go-sqletch (Apache-2.0, created 2026-08-01, v0.0.8 on 2026-10-16), is a separate generator that "deliberately does not replace" sqlc and whose template-language reference contains `@if-present`, `@choose`, `@when`, `@filter-tree`, `@order-by`, `@in` but no include/partial/macro construct for cross-query reuse — [go-sqletch README](https://github.com/moznion/go-sqletch); [go-sqletch template language reference](https://github.com/moznion/go-sqletch/blob/HEAD/docs/manual/02-template-language.md)

### Inferences
- The gap is real and long-standing: the same need (shared WHERE predicates, repeated joins, list/count/sum triplets) has been restated in the sqlc tracker from 2019 (#112) through 2024 (#2244 comments) without an implementation, and the maintainer's preferred answer (a Jinja-style preprocessor) was never built by anyone, inside or outside the project.
- The ecosystem's energy went into "dynamic queries" (optional clauses at runtime) rather than "fragment reuse" (compile-time sharing); none of the dynamic-query tools solve cross-query deduplication, and several (mpyw, vtuanjs, sqletch) explicitly keep the select list static per query.
- A fragment preprocessor would have to solve the two problems the #2244 thread already identified: parameter typing when one fragment is used against different tables, and loss of "the file is valid SQL" (editor highlighting, direct execution).

### Gaps
- No Reddit or Gophers Slack/Discord content could be fetched directly, so a community tool known only there would be missed.
- Private forks are invisible: issue #2021's author reports a private fork implementing derived-table injection, and blog.exe.dev describes a private sqlc fork; neither is published.

## KQ1: Which projects preprocess .sql files before `sqlc generate` (templating, includes, macros, partials)?

### Takeaway
No reusable, published preprocessor exists. The pattern is practised only as bespoke in-repo generators (kent, BiOME) and as scaffolding/CRUD generators that emit fresh query files from templates (pgxgen, sqlc-gen-queries, many project scaffolders). All are text-based (`text/template`), none document source-line mapping of sqlc errors, and none specifically handle `sqlc.arg/narg/slice/embed` beyond passing them through verbatim.

### Cited Findings

Bespoke in-repo pipelines (hand-written queries rendered from templates):
- respawn-llc/kent (Go, AGPL-3.0, 79 stars, created 2026-02-07, pushed 2026-10-17; SQLite engine) keeps query sources in `server/metadata/querysrc/queries.sql.tmpl` plus three partial files (`task_label_filter.sql.tmpl`, `task_dependency_filter.sql.tmpl`, `task_status_projection.sql.tmpl`); the main template defines reusable blocks with `{{define "boardSortOrder"}}`, `{{define "labelOrdinalSequence"}}`, `{{define "taskSessionProjectionFields"}}`, `{{define "taskSessionProjectionJoins"}}` and the `-- name:` headers and `sqlc.arg(...)` calls are written verbatim in the template — [queries.sql.tmpl](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querysrc/queries.sql.tmpl); [repo](https://github.com/respawn-llc/kent)
- kent's partials are parameterised with template data such as `.Indent`, `.TaskID`, `.LabelIDs`, `.FilterKind`, i.e. the SQL expression to bind is passed in as a string by the caller, so parameter naming is the author's responsibility — [task_label_filter.sql.tmpl](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querysrc/task_label_filter.sql.tmpl); [query_source_renderer.go](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querygen/query_source_renderer.go)
- kent's generator renders to `server/metadata/queries.sql`, runs `sqlc generate -f sqlc.yaml` via `os/exec`, deletes the rendered file in a `defer`, and then post-processes the generated Go (`annotateFile` wraps database-call errors); it is wired with `//go:generate sh -c "cd ../../.. && go run ./server/metadata/querygen generate"` — [querygen/main.go](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querygen/main.go); [sqlc_diagnostics.go](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/querygen/sqlc_diagnostics.go); [sqlitegen/generate.go](https://github.com/respawn-llc/kent/blob/HEAD/server/metadata/sqlitegen/generate.go)
- lsdch/BiOME (Go/Vue, no license, 0 stars, created 2025-01-18, pushed 2026-10-07; PostgreSQL) has `server/db/queries/templates/occurrences_summary.sql.tmpl` containing `{{- range .Queries }} -- name: {{.Name}} :many SELECT sqlc.embed(o), ... ORDER BY {{.OrderBy}} ...` and a generator that reads `internal/sqlcgen/config.yaml` (template, output, list of `{name, order_by}`) and writes `queries/generated/occurrences_summary_gen.sql` for sqlc — [occurrences_summary.sql.tmpl](https://github.com/lsdch/BiOME/blob/HEAD/server/db/queries/templates/occurrences_summary.sql.tmpl); [generator.go](https://github.com/lsdch/BiOME/blob/HEAD/server/db/internal/sqlcgen/generator.go)
- Coder evaluated "SQLc + Go templates" in 2023 and instead moved the dynamic/join queries to sqlx + Go templates (PR #6429, merged 2023-03-10), keeping sqlc for models and other queries; the noted downside was weaker SQL highlighting, especially in GoLand — [coder/coder issue #6426](https://github.com/coder/coder/issues/6426)
- Emyrk (Coder) in the sqlc tracker: "I have done a very similar thing with Go templates before feeding to SQLc while experimenting. The only downside to the macros is you lose SQL highlighting" (2023-09-26) and "you'd lose your source code being valid SQL. Right now that is a huge upside to SQLc" (2024-02-26) — [issue #2244](https://github.com/sqlc-dev/sqlc/issues/2244)

Non-Go preprocessors that could be wired in front of sqlc:
- dimfeld/sqlweld (Rust; 4 stars; created 2023-11-21; last push 2023-12-28) renders `.sql.tera` templates with `{% import "perm_check" as macros %}` and `{{ macros::perm_check(...) }}` into plain `.sql` files, motivated by "Permissions checks often look very similar between queries"; it uses `$[name]` placeholders and cites sqlx, not sqlc — [dimfeld/sqlweld README](https://github.com/dimfeld/sqlweld)

- go-sqlt/sqlt (formerly wroge/sqlt; the old URL redirects): MIT, 35 stars, created 2024-06-29, last commit 2025-11-22; "uses Go's template engine to create a flexible, powerful, and type-safe SQL builder and struct mapper" at runtime — [go-sqlt/sqlt](https://github.com/go-sqlt/sqlt)
- VauntDev/tqla: MIT, 103 stars, created 2023-07-10, last commit 2024-11-26; a `text/template` wrapper that replaces template values with driver placeholders (`tqla.WithPlaceHolder(tqla.Dollar)`), "does not attempt to do any sql validation"; the Vaunt launch post (2023-10-26) never mentions sqlc — [VauntDev/tqla](https://github.com/VauntDev/tqla); [dev.to/vaunt](https://dev.to/vaunt/dynamic-sql-template-with-golang-36hh)
- qjebbs/go-sqlf (the given name qjebbs/go-sqls redirects here): MIT, 0 stars, created 2023-04-10, pushed 2026-04-30, "building SQL queries by free combination of fragments" at runtime — [qjebbs/go-sqlf](https://github.com/qjebbs/go-sqlf)

### Inferences
- Both real pipelines (kent, BiOME) treat sqlc as a black box: errors from `sqlc generate` refer to the rendered file (kent even deletes it afterwards), so there is no mapping back to template lines; a library would need to add that.
- In kent, fragment parameters are threaded through template data as raw strings, which is the "inline" alternative to #2244's "embedded params struct" design; both approaches are visible in the wild only as proposals or private code.
- Scaffold/CRUD generators are a different product category (they create query files once, for editing) and should not be counted as fragment-reuse tools.

### Gaps
- Neither kent nor BiOME has a write-up, so there is no reported experience of maintaining the pipeline beyond the code itself.
- I found no Go project using gomplate, m4, Jinja (Python) or Mustache in front of sqlc; the `extension:tpl` and `extension:gotmpl` code searches for `sqlc.arg` returned zero files.

## KQ2: Do any sqlc codegen plugins or sqlc-gen-go forks add composability (builders, optional clauses, reusable column lists)?

### Takeaway
Yes for optional clauses and runtime builders (a lively 2025-2026 cluster: mpyw/sqlc-gen-go-dynamic, vtuanjs/sqlc-gen-go, IodeSystems/sqlc-go-codegen-metaquery, getangry/sqld, plus older yiplee/sqlc and projectdiscovery/sqlc-go-builder), but all operate within a single query and none offers reusable fragments or shared column lists across queries. Template-based plugins (sqlc-gen-from-template, sqlc-gen-template, NMFR/sqlc-template, donkeywon/sqlc-ext) template the *output code*, not the input SQL.

### Cited Findings

Forks of sqlc-gen-go adding dynamic clauses (text-based, directives in SQL comments so sqlc still parses plain SQL):
- mpyw/sqlc-gen-go-dynamic (MIT, 0 stars, created 2026-08-20, last commit 2026-09-22, "Status: v0, exploratory", no release) adds `/*%if e*/ … /*%elseif*/ … /*%else*/ … /*%end*/`, `/*%for x in xs*/`, and `/*%! … */` directives; conditions use expr-lang; it runs as a process or WASM plugin and accepts every sqlc-gen-go option — [README](https://github.com/mpyw/sqlc-gen-go-dynamic)
- Its documented authoring rules show how sqlc interacts with comment directives: directives must be indented because "sqlc treats a block comment starting at column zero as standalone ... and drops the whole line from Query.text"; "Keep the select list static"; "On SQLite, do not end a statement with a directive"; "Write sqlc.arg(name) rather than @name next to an operator, and always on MySQL"; placeholder numbering "runs off one counter per render" — [README](https://github.com/mpyw/sqlc-gen-go-dynamic)

### Inferences
- Parameter handling in the fork/plugin cluster converges on two mechanisms: (1) sqlc still types every parameter from the catalog, and (2) the plugin or runtime renumbers positional placeholders after dropping inactive clauses. ### Inferences
- The scarcity of application-level pipelines (2 found among thousands of sqlc users) suggests teams either tolerate duplication or move dynamic queries to builders rather than build a preprocessor; the cost of the lost "valid SQL" property is the most-cited reason.

### Gaps
- GitHub code search only indexes default branches of public repositories; private monorepos (where such pipelines are most likely) are invisible.
- Only the first page of each code-search result set was inspected (30 of 123 hits for `"-- name:" extension:tmpl "{{"`, most of which are sqlc's own codegen templates).
