Method note: findings marked "observed" come from reading the sqlc source at tag v1.31.1 (cloned 2026-10-19, commit a95e91d70ad9e1181253c333a1cfdd75ae4b95a5, "Release 1.31.1 (#4407)", 2026-04-22) and the v1.30.0 module in the local Go module cache, plus docs.sqlc.dev, the GitHub REST API (queried 2026-10-19), and the `main` branch as of 2026-10-19. ## KQ0. The `sqlc generate` pipeline end to end

### Takeaway
`sqlc generate` is a fixed, hook-free sequence: load config -> validate -> (optional cloud remote path) -> for every (sql block x output) pair in parallel: glob schema files -> parse DDL -> build catalog -> glob query files -> parse each file -> per statement: extract `-- name:` metadata, validate sqlc.* macros, rewrite named params/embeds, infer params and columns, expand `*`, splice text edits into the original SQL -> build a `plugin.GenerateRequest` -> run built-in Go/JSON generator or a process/WASM plugin -> write returned files under `out`. The only externally reachable seams are: the files named by `schema`/`queries` (inputs), the config file (`-f`), the plugin protocol (post-compile only), `pkg/cli.Run` (in-process invocation), `sqlc vet` CEL rules (post-compile), and the new `sqlc parse` subcommand (AST dump, v1.31.0).

### Cited Findings
- Entry point: the cobra `generate` command calls `Generate(ctx, dir, name, &Options{...})`, then writes every returned file with `os.MkdirAll` + `os.WriteFile(..., 0644)`; it never deletes stale files. `compile` runs the same `Generate` without writing (static check). Persistent flags: `-f/--file` alternate config, `--remote`, `--no-remote`. Subcommands registered: `compile` (checkCmd), `createdb`, `diff`, `generate`, `init`, `parse`, `version`, `verify`, `push`, `vet` — [internal/cmd/cmd.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/cmd.go)
- `Generate` = `o.ReadConfig` -> `config.Validate` -> `Env.Validate` (rejects process plugins when `SQLCDEBUG=processplugins=0`) -> if `cloud.project` set and `--remote`, `remoteGenerate` ships config+SQL to `remote.sqlc.dev` -> else `processQuerySets` — [internal/cmd/generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go); default remote hostname constant in [internal/remote/rpc.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/remote/rpc.go)
- `processQuerySets` builds one `OutputPair` per `gen.go`, per `gen.json`, and per `codegen[]` entry of each `sql[]` block, runs them in an `errgroup` limited to `runtime.GOMAXPROCS(0)`, joins every `schema`/`queries` path with the config directory (`filepath.Join(dir, s)`), calls `parse(...)` then `rp.ProcessResult(...)`; per-pair stderr is buffered and only flushed if something errored — [internal/cmd/process.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/process.go)
- `parse()` = `compiler.NewCompiler(sql, combo, parserOpts)` -> `c.ParseCatalog(sql.Schema)` -> `c.ParseQueries(sql.Queries, parserOpts)` -> `c.Result()`; parse errors are printed as `file:line:col: msg` with the filename made relative to the config dir (`printFileErr`) — [internal/cmd/generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go)
- `codegen()` builds the request with `codeGenRequest(result, combo)` and dispatches: `sql.Plugin != nil` -> `process.Runner{Cmd, Env, Format}` or `wasm.Runner{URL, SHA256, Env}`; `sql.Gen.Go != nil` -> in-process `ext.HandleFunc(golang.Generate)`; `sql.Gen.JSON != nil` -> in-process `genjson.Generate`; then `plugin.NewCodegenServiceClient(handler).Generate(ctx, req)` — [internal/cmd/generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go)
- `ProcessResult` places every returned file at `filepath.Join(g.dir, out, file.Name)` and rejects any path containing `..` or not prefixed by the absolute `out` dir ("invalid file output path") — [internal/cmd/generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go)
- The compiler object: `Compiler{conf, combo, catalog, parser, result, analyzer, client, selector, schema []string, databaseOnlyMode, expander}`; `NewCompiler` picks per engine: sqlite -> `sqlite.NewParser()`/`sqlite.NewCatalog()`/`newSQLiteSelector()`; mysql -> `dolphin.NewParser()`/`dolphin.NewCatalog()`; postgresql -> `postgresql.NewParser()`/`postgresql.NewCatalog()`; an optional database analyzer (`analyzer.Cached(...)`) is attached when `database` is configured and `analyzer.database` is enabled; `analyzer.database: "only"` plus `SQLCEXPERIMENT=analyzerv2` enables database-only mode with an `expander` for `SELECT *` — [internal/compiler/engine.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/engine.go)
- Schema parsing: `sqlpath.Glob(schemas)` -> for each file `os.ReadFile` -> `migrations.RemoveRollbackStatements` -> `migrations.RemovePsqlMetaCommands` (new in 1.31.0, #4390) -> `c.parser.Parse` -> `c.catalog.Update(stmt, c)` (the compiler itself is the `columnGenerator` used for views/CTAS) — [internal/compiler/compile.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/compile.go)
- Query parsing: `sqlpath.Glob(c.conf.Queries)` -> per file `c.parser.Parse(whole file)` -> per statement `c.parseQuery(stmt.Raw, src, o)`; a nil query (no name annotation) is skipped; duplicate names across all files error with `duplicate query name: X`; zero named queries errors with `no queries contained in paths ...`; `query.Metadata.Filename = filepath.Base(filename)` — [internal/compiler/compile.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/compile.go)
- `parseQuery` order: `validate.SqlcFunctions(stmt)` -> `source.Pluck(src, raw.StmtLocation, raw.StmtLen)` (raw text; empty -> "missing semicolon at end of file") -> `metadata.ParseQueryNameAndType` -> `validate.Cmd` -> `source.CleanedComments` + `metadata.ParseCommentFlags` -> analysis (`analyzeQuery`, or analyzer/db paths) -> if the text was edited, re-parse it ("edited query syntax is invalid") -> `source.StripComments(expanded)` -> `Query{RawStmt, Metadata, Params, Columns, SQL: trimmed, InsertIntoTable}` — [internal/compiler/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/parse.go)
- Built-in JSON generator (`gen.json: {out, filename (default codegen_request.json), indent}`) dumps the exact `GenerateRequest` plugins receive, which is the cheapest way to inspect compiled queries — [docs: Configuration reference](https://docs.sqlc.dev/en/latest/reference/config.html); [internal/config/config.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/config/config.go)
- The maintainers' own in-repo architecture notes (`CLAUDE.md` files) summarise the engine flow as "SQL String -> TiDB Parser -> TiDB AST -> sqlc AST -> Analysis/Codegen" and document walk/rewrite requirements for new AST nodes — [internal/engine/dolphin/CLAUDE.md](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/dolphin/CLAUDE.md); [internal/sql/rewrite/CLAUDE.md](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/CLAUDE.md); [internal/sql/ast/CLAUDE.md](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/ast/CLAUDE.md)

### Inferences
- There is no pre-parse hook, no "include", and no transform step anywhere between reading a `.sql` file and parsing it. A fragment-reuse library therefore has to run *before* sqlc (generate `.sql` files sqlc then reads) or *after* (plugin/vet), or wrap sqlc in-process via `pkg/cli`.
- Because output files are only ever written, never pruned, a preprocessor that renames generated query files must handle stale `.sql`/`.go` outputs itself.

### Gaps
- None for the pipeline shape itself; everything above is observed in source.

## KQ1. Configuration (sqlc.yaml / sqlc.json version 2)

### Takeaway
`queries` and `schema` are "path lists" (a single string or a YAML/JSON list) where each entry may be a file, a directory (listed one level deep, non-recursive), or a glob (`*?[]` expanded via `filepath.Glob`); only files ending in lowercase `.sql`, not hidden, and not down-migrations are used, and paths resolve relative to the config file's directory. There is no `include`, no generic env-var substitution (only `database.uri`/`servers[].uri` document `${VAR}`), no pre-generate hook, and unknown keys are rejected (`KnownFields(true)`). Generated `.sql` files in any directory are perfectly valid inputs. The top-level `options` map (keyed by plugin name) is the one place where arbitrary tool-specific YAML can live without breaking sqlc.

- `SQL` block keys: `name`, `engine` (`mysql`|`postgresql`|`sqlite` in v1.31.1), `schema Paths`, `queries Paths`, `database *{uri, managed}`, `strict_function_checks` (default false), `strict_order_by` (default true), `gen{go, json}`, `codegen []{out, plugin, options yaml.Node}`, `rules []string`, `analyzer{database: true|false|"only"}` — [internal/config/config.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/config/config.go); [docs: Configuration reference](https://docs.sqlc.dev/en/latest/reference/config.html)

### Inferences
- Because `v2ParseConfig` validates `plugins`, `sql`, `codegen` but never checks the keys of the top-level `options` map against declared plugins, a tool can keep its own settings under e.g. `options: { sqlcshare: {...} }` in the same `sqlc.yaml` and sqlc will ignore them (observed: only `combo.Global.Options[plug.Name]` is read, for a configured plugin). This is the only "free" slot in a v2 config; any other unknown key fails `KnownFields(true)`.
- Pointing `queries:` at a build directory (e.g. `queries: gen/sql`) is fully supported; combined with `-f build/sqlc.yaml` a tool can even generate the config. Globs make `queries: ["gen/*/queries"]` possible.
- `os.ReadDir` returns entries sorted by filename, and `filepath.Glob` results are lexical, so query processing order (and therefore error ordering) is deterministic per path entry; query names must be globally unique anyway.

### Gaps
- Where `${VAR}` in `database.uri` is actually expanded (likely in the analyzer/dbmanager when connecting) was not traced; the docs claim is relied upon.
- Exact `migrations.IsDown` filename patterns were not read.

## KQ2. Query file processing: annotations, statement splitting, comments, errors

### Takeaway
Each query file is parsed whole by the engine parser; each statement's raw text (`StmtLocation`/`StmtLen`) *includes the comments preceding it*, and `metadata.ParseQueryNameAndType` scans that text line by line for a comment line that is exactly `-- name: Name :cmd` (also `/* name: Name :cmd */` and, for MySQL, `# name: Name :cmd`), split on single spaces into exactly four tokens. Full-line comments other than the name line become `Query.comments` (emitted as Go `//` doc comments on the method and passed to plugins); inline/trailing comments and multi-line block comments stay inside the query text. Errors are reported as `relative/path.sql:line:col: message` where the file is whatever path sqlc read (so a generated file, not its source).

### Cited Findings
- Commands recognised: `:exec`, `:execresult`, `:execrows`, `:execlastid`, `:many`, `:one`, `:copyfrom`, `:batchexec`, `:batchmany`, `:batchone` (constants `CmdExec`...`CmdBatchOne`) — [internal/metadata/meta.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/metadata/meta.go); semantics and the PostgreSQL+pgx-only restriction on `:batch*` — [docs: Query annotations](https://docs.sqlc.dev/en/latest/reference/query-annotations.html)
- `ParseQueryNameAndType(text, commentStyle)`: iterates lines; a line starting with `--`/`/*`/`#` is considered only if the engine's `CommentSyntax` allows it; if the remainder starts with `name` and contains `:` it must start with exactly `" name: "` else `invalid metadata: <line>`; the trimmed line is split on `" "`; a `/*` line drops its trailing `*/` token; 3 tokens -> "missing query type [...]", not 4 -> "invalid query comment"; unknown cmd -> "invalid query type"; name must be a Go identifier; first match wins; no match -> `"", "", nil` (query silently ignored) — [internal/metadata/meta.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/metadata/meta.go)
- Comment syntax per engine: PostgreSQL `{Dash, SlashStar}`; MySQL `{Dash, SlashStar, Hash}`; SQLite `{Dash, SlashStar}` — [postgresql/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/postgresql/parse.go), [dolphin/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/dolphin/parse.go), [sqlite/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/sqlite/parse.go)
- Statement location per engine (observed): PostgreSQL copies pg_query's `raw.StmtLocation`/`raw.StmtLen`; MySQL computes `loc = strings.Index(blob, stmt.Text())` and `StmtLen = len(text)` minus a trailing `;`; SQLite starts each statement at the previous statement's stop+2 (so inter-statement text, including comments, belongs to the next statement) and skips statements that convert to `ast.TODO` — same three files as above
- `validate.Cmd`: `:copyfrom` requires `INSERT ... VALUES (<params only>)` with exactly one row, no `ON CONFLICT`, `WITH`, `RETURNING` or `INSERT ... SELECT`; `:batch*` requires at least one parameter; `:one/:many/:batchone/:batchmany` on INSERT/UPDATE/DELETE require a `RETURNING` clause ("query %q specifies parameter %q without containing a RETURNING clause") — [internal/sql/validate/cmd.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/validate/cmd.go)
- `source.CleanedComments` collects every full-line comment (prefix-aware) and `metadata.ParseCommentFlags` interprets tokens starting with `@`: `@param <name> <rest>` fills `Metadata.Params`, `@sqlc-vet-disable [rules...]` fills `RuleSkiplist`, any other `@token` sets a flag — [internal/metadata/meta.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/metadata/meta.go); [internal/source/code.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/source/code.go)
- `source.StripComments(sql)`: trims, scans line by line; drops lines starting with `-- name:`, `/* name:...*/`, `# name:`; lines starting with `--`, `#`, or single-line `/* ... */` are removed and stored as comments (prefix stripped); `/*+` MySQL optimizer hints are kept in the SQL (1.31.0, #4382); every other line (including lines with trailing `-- ...` comments and the first line of a multi-line `/* ... */` block) is kept verbatim in the query text — [internal/source/code.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/source/code.go)
- Go codegen: `comments := query.Comments`; with `emit_sql_as_comment` the query text lines are appended; the generated constant is `const <name> = `-- name: <MethodName> <cmd>\n<text>`` (the name line is re-synthesised by the template) and comments are rendered as `//` lines above methods/interface entries — [internal/codegen/golang/result.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/codegen/golang/result.go); [templates/stdlib/queryCode.tmpl](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/codegen/golang/templates/stdlib/queryCode.tmpl); [templates/pgx/interfaceCode.tmpl](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/codegen/golang/templates/pgx/interfaceCode.tmpl)
- Error model: `multierr.Error.Add(filename, src, loc, err)` computes `line, column` from the byte offset via `source.LineNumber` (skipping whitespace and `--` comments after the offset), or uses `sqlerr.Error.Line/Column` when the engine supplied them; printed as `%s:%d:%d: %s` with the filename relative to the config dir — [internal/multierr/errors.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/multierr/errors.go); [internal/cmd/generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go)
- Engine syntax errors: PostgreSQL `normalizeErr` maps `parser.Error{Message, Lineno, Cursorpos}` to `sqlerr.Error{Message, Line, Location}`; MySQL parses TiDB's `line N column M ...` message with a regex into `sqlerr.Error{Line, Column}`; SQLite's ANTLR error listener keeps only the message (`errors.New(el.err)`) — engine `parse.go` files linked above
- A semantic error inside a query (unknown column etc.) is reported at `stmt.Raw.Pos()` unless the error is a `*sqlerr.Error` with a non-zero `Location` (e.g. `column "x" does not exist`, code 42703, located at the ResTarget) — [internal/compiler/compile.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/compile.go); [internal/compiler/output_columns.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/output_columns.go)

### Inferences
- For a preprocessor that emits generated `.sql`, sqlc's diagnostics will cite the *generated* file and its line/column; mapping back to the authored source requires the tool to keep a line map (and, for SQLite, note that syntax errors carry no position at all and will print `file:1:1`).
- The `-- name:` matcher is whitespace-strict (single spaces, lowercase `name:`), so generated files must emit exactly `-- name: Foo :one`.
- Because `Query.comments` survives into the plugin request and into Go doc comments, a preprocessor can carry provenance (e.g. `-- fragment: WorkspaceCheck`) through to a custom plugin; tokens starting with `@` would additionally be parsed as flags.
- MySQL's statement text being located via `strings.Index(blob, stmt.Text())` means TiDB's `Text()` must already include the leading comment (otherwise `-- name:` could never be found for MySQL); not verified against TiDB source.

### Gaps
- Whether TiDB's statement `Text()` includes preceding comments was not verified in the TiDB parser source (inferred from the fact that MySQL annotations work).

## KQ3. Macro rewriting and parameter numbering

### Takeaway
Rewriting is text-splicing driven by the AST: `rewrite.NamedParameters` finds `sqlc.arg/narg/slice(...)` calls and `@name` operator expressions, replaces them in the AST with `ParamRef` nodes numbered by a `named.ParamSet`, and records `source.Edit`s against the original text; `rewrite.Embeds` turns `sqlc.embed(t)` into a `t.*` column reference; `expand` turns every `*` into an explicit column list; finally `source.Mutate` applies all edits from highest offset to lowest. Numbering: PostgreSQL and SQLite dedupe repeated names to one number (`$n` / `?n`), MySQL gives each occurrence a fresh `?`. The code assumes macros are on one line with canonical spacing.

### Cited Findings
- Pre-check `validate.SqlcFunctions`: any `sqlc.<fn>` call must be `arg`, `narg`, `slice` or `embed` (else `FunctionNotFound`), with exactly one argument that is an `A_Const` or `ColumnRef` (so `sqlc.arg(name)` and `sqlc.arg('name')` both work) — [internal/sql/validate/param_style.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/validate/param_style.go)
- `validate.ParamRef` collects all `ast.ParamRef`s: mixing `$1`-style (`Dollar`) and `?`-style is an error ("can not mix $1 format with ? format"); numbers must be contiguous from 1 (else `42P18 could not determine data type of parameter $N`); returns the used-number set and `dollar` — [internal/sql/validate/param_ref.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/validate/param_ref.go)
- Analysis order in `_analyzeQuery`: `validate.ParamRef` -> `rewrite.NamedParameters(engine, raw, numbers, dollar)` -> INSERT table/column validation -> `validate.FuncCall` -> `validate.In` -> `rangeVars` -> `findParameters` -> `uniqueParamRefs` -> sort refs by source location (MySQL or `?` style) or by number (`$` style) -> `rewrite.Embeds` -> `buildQueryCatalog` (CTEs) -> `resolveCatalogRefs` (parameter types) -> `outputColumns` -> `expand` (star edits) -> `source.Mutate(query, edits)` — [internal/compiler/analyze.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/analyze.go)
- Detection: `named.IsParamFunc` = `FuncCall` with `Func.Schema == "sqlc"` and name `arg|narg|slice`; `named.IsParamSign` = `A_Expr` whose operator name joins to `@`; a third case handles `@foo::type` casts — [internal/sql/named/is.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/is.go); [internal/sql/rewrite/parameters.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/parameters.go)
- Replacement text: for `sqlc.*` calls: MySQL -> `?`, SQLite -> `?<n>`, PostgreSQL (or any engine when the query is `$`-style) -> `$<n>`; `sqlc.slice` under MySQL/SQLite/non-dollar -> `/*SLICE:<name>*/?` (the Go generator rewrites this at runtime); for `@name`: MySQL or non-dollar -> `?`, SQLite -> `?<n>`, else `$<n>`; the `Old` text is reconstructed as `sqlc.arg(name)` / `sqlc.arg('name')` with a TODO stating the code "assumes that sqlc.arg(name) / sqlc.narg(name) is on a single line with no extraneous spaces ... except between the function name and argument" and likewise "assumes that @foo is on a single line" — [internal/sql/rewrite/parameters.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/parameters.go)
- `ParamSet.Add`: `hasNamedSupport = engine != mysql`; when a name is already present and the engine has named support, the first assigned number is returned (dedupe); otherwise the next free number is allocated and recorded in `namedLocs[name]`; pre-existing positional numbers (from `$n`) are reserved as unnamed; unit test shows `named`: p1->1, p1->1, p2->2 vs `unnamed`: p1->1, p1->2, p2->3 — [internal/sql/named/param_set.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/param_set.go); [param_set_test.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/param_set_test.go)
- Nullability of parameters: `Param.NotNull()` precedence user-NotNullable > user-Nullable (`sqlc.narg`) > inferred NotNull > inferred Null > unspecified (defaults to nullable); inference comes from the compared catalog column (`named.NewInferredParam(key, c.IsNotNull)` in `resolveCatalogRefs`) — [internal/sql/named/param.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/param.go); [internal/compiler/resolve.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/resolve.go)
- Docs: `@name` "is not supported in MySQL", there is no nullable form of `@`, `sqlc.narg` forces nullable, `sqlc.slice` "can't be used with prepared statements", `sqlc.embed(table)` expands to `table.*` and yields one struct field per embedded table — [docs: Named parameters](https://docs.sqlc.dev/en/latest/howto/named_parameters.html); [docs: Macros](https://docs.sqlc.dev/en/latest/reference/macros.html)
- Engine mapping of `@`: PostgreSQL parses `@name` as an `A_Expr` with operator `@` (hence detected); MySQL converts TiDB `VariableExpr` to `ast.VariableExpr` which is *not* detected and is preserved as a user variable; SQLite converts `NAMED_BIND_PARAMETER` tokens to the `A_Expr "@"` form with the sigil stripped (`n.GetText()[1:]`) and `NUMBERED_BIND_PARAMETER` (`?`, `?NNN`) to `ParamRef{Dollar: len(text) > 1}` — [internal/sql/named/CLAUDE.md](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/named/CLAUDE.md); [internal/engine/sqlite/convert.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/engine/sqlite/convert.go)
- `rewrite.Embeds` replaces `sqlc.embed(x)` with a `ColumnRef{x, *}` and an `Embed{Table: x, Node}`; `expand` later uses `embed.Orig()` (`sqlc.embed(x)`) as the exact old text to replace with the column list; `outputColumns` emits a single `Column{Name: x, EmbedTable: x}` for it — [internal/sql/rewrite/embeds.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/embeds.go); [internal/compiler/expand.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/expand.go); [internal/compiler/output_columns.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/output_columns.go)
- `expand` rewrites `*` / `t.*` in SELECT target lists and `RETURNING` lists into explicit, dialect-quoted column lists (reserved words and non-lowercase identifiers are quoted; MySQL uses backticks), prefixing with the table name when a column name is duplicated across source tables; the SQLite selector wraps `jsonb` columns in `json(col)` — [internal/compiler/expand.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/expand.go)
- `source.Mutate` sorts edits by descending location and fails on overlap ("2 edits overlap") or out-of-bounds — [internal/source/code.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/source/code.go)
- 1.31.0 fixed "Dedupe `sqlc.arg` parameters wrapped in a type cast for MySQL (#4384)" — [changelog v1.31.0](https://docs.sqlc.dev/en/latest/reference/changelog/v1.31.0.html)
- In database-analyzer modes the same rewrite still runs first (`inferQuery`), the analyzer only overrides types that are not `any`, and star expansion must have changed the text or sqlc errors "star expansion failed for query" — [internal/compiler/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/parse.go); [internal/compiler/analyze.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/analyze.go)

### Inferences
- A fragment preprocessor should emit macros in canonical form (`sqlc.arg(name)` with no inner spaces, one per line segment) and avoid splitting `@name` across lines; otherwise the text edit `Old` string will not match and the spliced SQL will be corrupt or fail the post-edit re-parse.
- Repeating a parameter name across several fragments is safe on PostgreSQL/SQLite (deduped to one placeholder) but on MySQL yields one `?` per occurrence; how the Go generator binds the repeated name for MySQL was not verified here (see Gaps).
- Fragments that contain `*` are fine: expansion happens on the final assembled query.

### Gaps
- Go generator handling of the same named parameter appearing at several positional slots under MySQL (whether the argument is passed twice automatically) was not read.
- Whether SQLite's `NAMED_BIND_PARAMETER` lexer token covers `:name` and `$name` in addition to `@name` was not checked in the grammar.

## KQ4. Parsing engines and AST conversion; deparser availability

### Takeaway
PostgreSQL uses `pganalyze/pg_query_go/v6 v6.2.2` (cgo) or the pure-Go `wasilibs/go-pgquery` build on Windows/`CGO_ENABLED=0`; MySQL ("dolphin") uses the TiDB parser at pseudo-version `v0.0.0-20260418072757-ce92298d1124`; SQLite uses an ANTLR4 grammar derived from bkiers/sqlite-parser with `antlr4-go/antlr/v4 v4.13.1`. ### Inferences
- `pg_query_go/v6` tracks the PostgreSQL 17 grammar (pganalyze's major-version convention); not verified against the pg_query_go README in this research.
- An external tool wanting "the same parse as sqlc" has three practical options: (a) depend directly on `pg_query_go`/TiDB parser/ANTLR grammar (what sqlc does), (b) shell out to `sqlc parse --dialect` and consume JSON (but the JSON shape of interface-typed fields is untyped Go encoding, see Gaps), or (c) copy `internal/sql/ast` + `astutils` + engine converters into the tool (MIT permits it; it is what sqlc-gen-go did for codegen).

## KQ5. Catalog building and type inference (views, CTEs, subqueries, RETURNING, nullability, embed)

### Takeaway
The catalog is built only from DDL statements it recognises; `CREATE VIEW` and `CREATE TABLE AS` are stored as ordinary tables whose columns are produced by the compiler's own `OutputColumns` inference, so a view carries the same inferred names, types and NOT NULL flags that a direct query would get, and is then usable in queries, star expansion and (inferred) `sqlc.embed`. CTEs are resolved per query (`QueryCatalog.ctes`), subselects and `RETURNING` are supported, and nullability is a small rule set: catalog `NOT NULL` flag, LEFT/RIGHT/FULL join demotion via `isTableRequired`, constants/comparisons/`IS NULL`/`EXISTS` not-null, `COALESCE` not-null if any constant or not-null arg, functions by catalog `ReturnTypeNullable`, everything else `any`/nullable.

### Cited Findings
- `catalog.Update` dispatches on: `AlterTableStmt`, `AlterTableSetSchemaStmt`, `AlterTypeAddValueStmt`, `AlterTypeRenameValueStmt`, `AlterTypeSetSchemaStmt`, `CommentOn{Column,Schema,Table,Type,View}Stmt`, `CompositeTypeStmt`, `CreateEnumStmt`, `CreateExtensionStmt`, `CreateFunctionStmt`, `CreateSchemaStmt`, `CreateTableStmt`, `CreateTableAsStmt` (with `columnGenerator`), `ViewStmt` (with `columnGenerator`), `Drop{Function,Schema,Table,Type}Stmt`, `Rename{Column,Table,Type}Stmt`, and nested `List` — [internal/sql/catalog/catalog.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/catalog/catalog.go)
- `createView(stmt, colGen)`: `cols, err := colGen.OutputColumns(stmt.Query)`; stored as `Table{Rel: view name, Columns: cols}` in `schema.Tables`; `CREATE OR REPLACE` replaces in place, otherwise an existing relation errors — [internal/sql/catalog/view.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/catalog/view.go); `createTableAs` is identical minus replace — [internal/sql/catalog/table.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/catalog/table.go)

- Go models: `result.go` builds one struct per `schema.Tables` entry of the plugin catalog (views included because they are tables there); `omit_unused_structs` prunes unreferenced ones — [internal/codegen/golang/result.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/codegen/golang/result.go)
- Community observation on the "views as fragments" workaround: "The current workaround is to define it as a view, but you cannot use things such as `sqlc.embed` in a view" (Emyrk, 2023-07-13) and a dedicated proposal to expand views at generation time, issue #2491 (open, 0 comments) — [issue #2244](https://github.com/sqlc-dev/sqlc/issues/2244); [issue #2491](https://github.com/sqlc-dev/sqlc/issues/2491)

### Inferences
- Nullability through a view is preserved: the view's columns are computed once (including LEFT JOIN demotion) and stored as `IsNotNull`; a later `SELECT ... FROM view` copies that flag, and a LEFT JOIN onto the view applies `isTableRequired` by the view's name. Column *names* are the view's output names (aliases honoured). What degrades is type identity: `OutputColumns` stores `Type: ast.TypeName{Name: col.DataType}`, so schema-qualified types become a dotted `Name` with empty `Schema`; whether this changes Go type mapping for enums/composites in non-default schemas was not tested.
- `sqlc.embed(view)` should work because views are catalog tables and the Go generator has a struct for every catalog table; untested.
- Fragments that live *inside* a view definition cannot use `sqlc.arg`/`sqlc.embed` because the view body is parsed as DDL with no macro rewriting, and views cannot take parameters; this is the structural reason views are not a full substitute for fragment reuse (observed: schema path has no rewrite step; the embed limitation is from the issue thread).

### Gaps
- No end-to-end test was run to confirm view nullability/type behaviour; the conclusions are from code reading.

## KQ6. Codegen plugin protocol, runtimes, and sqlc-gen-go status

### Takeaway
Plugins implement `service CodegenService { rpc Generate(GenerateRequest) returns (GenerateResponse) }`. They receive `Settings`, the `Catalog`, and `Query{text, name, cmd, columns, params, comments, filename, insert_into_table}` where `text` is the *compiled* SQL (macros rewritten, `*` expanded, name line stripped); they never see the raw SQL, the AST, the full path, or the config beyond `Settings`, and they can only return files, which sqlc confines to `out`. Process plugins get protobuf (or JSON) on stdin with the gRPC method name as argv[1]; WASM plugins run under wazero/WASI with the same stdin/stdout contract, a sha256-keyed cache, and `pg_catalog`/`information_schema` stripped. Plugins run strictly after compilation (confirmed in `codegen()`); the built-in Go generator remains in-tree, while sqlc-gen-go is a separately released extraction (v1.6.0, 2026-04-20) whose README download URL currently 404s.

### Cited Findings

### Inferences
- A custom Go codegen is run either by forking sqlc-gen-go (WASM via `file://`, or `process.cmd` pointing at the built binary) or by writing a fresh plugin against `plugin-sdk-go`'s `plugin` package; because plugin-sdk-go has not been released since 2023-11 while `codegen.proto` in sqlc now has `Column.unsigned` (16) and `array_dims` (17), a new plugin should probably regenerate Go types from sqlc's `protos/plugin/codegen.proto` rather than trust the SDK's copy (whether the SDK already has those fields was not checked).
- The plugin layer is viable for the *Go side* of a fragment feature (e.g. generating shared param structs from markers in `Query.comments`), but not for the SQL side.

### Gaps
- Whether `plugin-sdk-go v1.23.0`'s `plugin.Column` includes fields 16/17 was not verified.
- Why the 1.6.0 WASM is missing from downloads.sqlc.dev (packaging lag vs. intentional) is unknown.

## KQ7. Importability and licensing

### Takeaway
Only `github.com/sqlc-dev/sqlc/pkg/cli` (`Run(args []string) int`) is importable; every parser, compiler, catalog and codegen package is under `internal/` and the Go toolchain refuses to import them from another module. The code is MIT-licensed, so vendoring/copying is legal with attribution and practical for self-contained packages (`internal/sql/ast`, `astutils`, `source`, `metadata`, `named`), but the module requires Go 1.26 and the PostgreSQL parser needs cgo (or the slower wasm build).

### Cited Findings
- `pkg/cli`: "package cli exposes the command-line interface for sqlc. It can be used to run sqlc from Go without the overhead of creating a child process ... `os.Exit(sqlc.Run(os.Args[1:]))`"; `Run` wraps `internal/cmd.Do(args, os.Stdin, os.Stdout, os.Stderr)` — [pkg/cli/cli.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/pkg/cli/cli.go)
- `pkg/` contains only `cli`; `internal/` contains `analysis, analyzer, bundler, cache, cmd, codegen, compiler, config, constants, dbmanager, debug, endtoend, engine, ext, inflection, info, metadata, migrations, multierr, opts, pattern, pgx, plugin, quickdb, remote, rpc, shfmt, source, sql, sqltest, tools, tracer, vet, x` — directory listing of the v1.31.1 tree ([repository root](https://github.com/sqlc-dev/sqlc/tree/v1.31.1))
- Go rule: "An import of a path containing the element 'internal' is disallowed if the importing code is outside the tree rooted at the parent of the 'internal' directory" — [Go command docs: Internal Directories](https://pkg.go.dev/cmd/go#hdr-Internal_Directories)
- License MIT (repo `LICENSE`; GitHub API `license: MIT`) — [LICENSE](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/LICENSE)
- Root `placeholder.go`: "This is a dummy file that allows SQLC to be 'installed' as a module and locked using go.mod and then run using 'go run github.com/sqlc-dev/sqlc'" — [placeholder.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/placeholder.go)
- `gomod_test.go` guards that go.mod never contains `replace` directives because they break `go install github.com/sqlc-dev/sqlc/cmd/sqlc@latest` (issue #4397; fixed in 1.31.1 #4401) — [gomod_test.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/gomod_test.go); [changelog v1.31.1](https://docs.sqlc.dev/en/latest/reference/changelog/v1.31.1.html)
- Module requires `go 1.26.0` (toolchain go1.26.2 at v1.31.1; go1.26.5 on main) — [go.mod @ v1.31.1](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/go.mod); [go.mod @ main](https://github.com/sqlc-dev/sqlc/blob/main/go.mod)
- sqlc-gen-go demonstrates the copy-out pattern: it is "extracted from sqlc", depends only on plugin-sdk-go, and is "read-only" (synced from sqlc commits) — [sqlc-gen-go README](https://github.com/sqlc-dev/sqlc-gen-go/blob/main/README.md)
- Install docs still say "Installing recent versions of sqlc requires Go 1.21+" (stale relative to go.mod) — [docs: Installing sqlc](https://docs.sqlc.dev/en/latest/overview/install.html)

### Inferences
- An in-process wrapper (`sqlcshare generate` -> write fragments-expanded `.sql` -> `cli.Run([]string{"generate", "-f", ...})`) is feasible and avoids a sqlc binary dependency, at the cost of pulling sqlc's full dependency tree (TiDB parser, wazero, pgx, cel-go) and requiring Go 1.26+ and cgo for the fast PostgreSQL parser.
- Copying `internal/sql/ast` + `astutils` + the engine converters is the only way to get sqlc's exact AST in-process; keeping such a copy in sync is the main maintenance cost (the upstream `ast` package changed in dozens of files between 1.30.0 and 1.31.1 per the directory diff).

### Gaps
- None.

## KQ8. `sqlc vet` and `sqlc verify`

### Takeaway
`sqlc vet` evaluates CEL rules against `query.sql` (the compiled text, after rewriting), `query.name`, `query.cmd`, `query.params[].number`, `config.*`, and optional `postgresql.explain`/`mysql.explain`; it can therefore enforce textual conventions (e.g. a required marker string) but cannot see raw SQL, comments, or fragment provenance. `sqlc verify` is a sqlc Cloud feature comparing pushed archives.

### Cited Findings
- CEL environment: `cel.Variable("query", vet.Query)`, `config` (vet.Config), `postgresql` (vet.PostgreSQL), `mysql` (vet.MySQL), with `cel.StdLib()`; `vetQuery` sets `Sql: q.Text`, `Cmd: strings.TrimPrefix(q.Cmd, ":")`, `Params[].Number` from the same `plugin.Query` used for codegen — [internal/cmd/vet.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/vet.go)
- vet proto: `Query{sql, name, cmd, params[]{number}}`, `Config{version, engine, schema[], queries[]}`, `PostgreSQLExplain{plan{node_type, total_cost, plan_rows, ...}}`, `MySQLExplain{query_block{...}}` — [protos/vet/vet.proto](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/protos/vet/vet.proto)
- Docs: rules in top-level `rules:` with `name`, `rule`, `message`; attached per package via `sql[].rules`; examples `query.sql.contains("DELETE")`, `query.params.size() > 1`, `query.cmd == "exec"`, `postgresql.explain.plan.node_type == 'Seq Scan'`; `@sqlc-vet-disable [rule...]` in query comments; built-in `sqlc/db-prepare` needs a database; `SQLCDEBUG=dumpvetenv=1`/`dumpexplain=1` — [docs: vet](https://docs.sqlc.dev/en/latest/howto/vet.html)
- Per-query rule skipping (`RuleSkiplist`) shipped in 1.28.0/1.29.0 — [changelog v1.29.0](https://docs.sqlc.dev/en/latest/reference/changelog/v1.29.0.html)
- `sqlc verify --against <tag>` creates a `quickdb` client from `cloud` config (default host `grpc.sqlc.dev`) — [internal/cmd/verify.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/verify.go); [internal/quickdb/rpc.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/quickdb/rpc.go); docs: "`push` is powered by sqlc Cloud" and verify "analyzes existing queries against new schema changes" (both added v1.24.0) — [docs: push](https://docs.sqlc.dev/en/latest/howto/push.html); [docs: verify](https://docs.sqlc.dev/en/latest/howto/verify.html)

### Inferences
- A fragment tool could ship a vet rule such as `!query.sql.contains("/* sqlcshare */")` to flag hand-written queries that bypass the preprocessor, provided the marker is an *inline* comment (full-line comments are stripped out of `query.sql`).
- vet is not a hook for rewriting; it only reports.

### Gaps
- None.

## KQ11. Integration-point matrix for a fragment-reuse library (per pipeline stage)

### Takeaway
Viable hooks, in order of leverage: (1) pre-generate preprocessing that writes expanded `.sql` files sqlc reads via `queries`/`schema` paths (the only place SQL text can be changed); (2) in-process orchestration through `pkg/cli.Run` or `go tool sqlc`; (3) a codegen plugin that consumes `Query.comments`/`text` to generate Go-side helpers (post-compile only); (4) `sqlc vet` CEL rules as an enforcement gate; (5) the top-level `options` map as a config carrier. Not viable without forking: parse-time hooks, AST-level rewriting, catalog injection, or changing query text from a plugin.

### Cited Findings
- Stage: config load. Hook: none inside sqlc; external: `-f` alternate config path and relative-path resolution against the config directory; `queries`/`schema` accept files, dirs, globs, lists — [internal/cmd/cmd.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/cmd.go); [internal/sql/sqlpath/read.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/sqlpath/read.go)
- Stage: query discovery/reading. Hook: the files themselves; sqlc reads bytes with `os.ReadFile` and parses verbatim — [internal/compiler/compile.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/compile.go)
- Stage: parse/rewrite/infer. Hook: none; constraints a generator must respect: exact `-- name:` syntax, one-line canonical macros, no `$n`/`?` mixing, contiguous `$n` numbering, trailing semicolon, statement text includes leading comments — [internal/metadata/meta.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/metadata/meta.go); [internal/sql/rewrite/parameters.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/rewrite/parameters.go); [internal/sql/validate/param_ref.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/validate/param_ref.go)
- Stage: catalog. Hook: schema files (also generated if desired); native reuse primitives sqlc already understands: `CREATE VIEW` (columns inferred), CTEs, functions — [internal/sql/catalog/view.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/catalog/view.go); [internal/compiler/query_catalog.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/compiler/query_catalog.go)
- Stage: codegen. Hook: process/WASM plugin or forked sqlc-gen-go; input is compiled `Query` + `Catalog` + `plugin_options`/`global_options`; output confined to `out` — [protos/plugin/codegen.proto](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/protos/plugin/codegen.proto); [internal/cmd/generate.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/generate.go)
- Stage: output. Hook: none; files are overwritten, never pruned; `sqlc diff` compares — [internal/cmd/cmd.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/cmd.go)
- Stage: lint. Hook: `rules[]` CEL over compiled text — [docs: vet](https://docs.sqlc.dev/en/latest/howto/vet.html)
- In-process: `pkg/cli.Run` — [pkg/cli/cli.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/pkg/cli/cli.go)
- Introspection without a plugin: `gen.json` dumps the full `GenerateRequest`; `sqlc parse --dialect` dumps ASTs; `SQLCDEBUG=dumpast=1,dumpcatalog=1` — [internal/config/config.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/config/config.go); [internal/cmd/parse.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/cmd/parse.go); [internal/opts/debug.go](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/opts/debug.go)

### Inferences
- The architecture that fits every observed constraint: a Go CLI/library that (a) reads fragment definitions and query templates (valid SQL with marker comments, so editors still highlight them), (b) expands them into a generated query directory using text splicing with a source map, (c) emits canonical macros and `-- name:` lines, (d) optionally rewrites sqlc's `file:line:col` diagnostics back to the authored files, (e) invokes sqlc via `pkg/cli.Run` or `go tool sqlc`, and (f) optionally ships a vet rule and/or a thin plugin for shared param structs. Engine differences the expander must model: `@name` unsupported on MySQL (use `sqlc.arg`), MySQL duplicates placeholders for repeated names, SQLite emits `?n`, `sqlc.slice` semantics differ between PostgreSQL (`$n`) and MySQL/SQLite (`/*SLICE:*/?`).

### Gaps
- No empirical measurement of how sqlc's diagnostics behave on multi-fragment generated files was made; a prototype would be needed to confirm the source-map approach.
