# sqlc official capabilities for sharing and re-using SQL across queries (state as of 2026-10-19)

Scope note: "latest release" below means **v1.31.1 (2026-04-22)**. The user's installed v1.30.0 (2025-09-01) is two releases behind. docs.sqlc.dev/en/latest tracks the `main` branch, so a few documented commands (`sqlc analyze`, `sqlc fmt`, extra `parse` dialects) exist on `main` but not in any release; these are flagged explicitly wherever they appear.

## Key Question 1: Built-in macros (sqlc.arg, sqlc.narg, sqlc.slice, sqlc.embed, newer ones): semantics, version introduced, relevance to re-use

### Takeaway
sqlc ships exactly four `sqlc.*` macros (`arg`, `narg`, `slice`, `embed`) plus the `@name` shorthand; none of them lets you share SQL text between queries. `sqlc.embed` is the only one framed as "re-use", and it re-uses generated Go model structs for a table's columns inside one query, not SQL. Every proposed macro for fragments or dynamic clauses (`sqlc.fragment`, `sqlc.switch`, `sqlc.optional`, `sqlc.dynamic`, `sqlc.sort`, `sqlc.nembed`, `sqlc.view`) is unmerged.

### Cited Findings
- The official Macros reference page documents exactly four macros: `sqlc.arg` ("names a query parameter... expands to an engine-specific placeholder"), `sqlc.narg` ("works like sqlc.arg but always marks the parameter as nullable"), `sqlc.slice` ("for drivers that don't support passing slices to the IN operator... builds the correct number of parameters at runtime... can't be used with prepared statements"), and `sqlc.embed` ("reuses existing model structs across queries to reduce manual serialization"; `sqlc.embed(students)` expands to `students.*` and the row struct gets nested `Student`/`TestScore` fields). No other macros are listed. — [Macros reference](https://docs.sqlc.dev/en/latest/reference/macros.html)
- The dedicated macro docs page was first added in v1.21.0 (2023-09-06) via PR #2698 "docs: Document sqlc.* macros". — [v1.21.0 release](https://github.com/sqlc-dev/sqlc/releases/tag/v1.21.0)
- `sqlc.arg('argname')` form: added in v1.1.0 (2020-03-17): "Allow sqlc.arg('argname') form for named params (#351)". — [v1.1.0 release](https://github.com/sqlc-dev/sqlc/releases/tag/v1.1.0)
- `@name` shorthand: documented as "a shortcut for sqlc.arg()"; "The @ operator as a shortcut for sqlc.arg() is not supported in MySQL"; "There is no nullable equivalent of the @ syntax". — [Naming parameters](https://docs.sqlc.dev/en/latest/howto/named_parameters.html)
- `sqlc.narg`: added in v1.14.0 (2022-06-10): "UPDATED: sqlc.narg() - allow user-specified nullability (#1536)" and "docs: add documentation for sqlc.narg() (#1580)". — [v1.14.0 release](https://github.com/sqlc-dev/sqlc/releases/tag/v1.14.0); Kyle Conroy confirmed on 2022-06-12: "1.14.0 includes `sqlc.narg` which generates nullable arguments." — [Issue #200 comment](https://github.com/sqlc-dev/sqlc/issues/200#issuecomment-1153232389)
- `sqlc.slice`: added in v1.18.0 (2023-04-27) via "Add sqlc.slice() to support IN clauses in MySQL (#695) by @Jille in PR #1816"; the v1.18.0 notes say "This feature is only supported in MySQL and cannot be used with prepared queries." — [v1.18.0 release](https://github.com/sqlc-dev/sqlc/releases/tag/v1.18.0). SQLite support for the `sqlc.*` functions came in v1.19.0 (2023-07-06) via "feat(sqlite) add support sqlc functions (#2274)". — [v1.19.0 release](https://github.com/sqlc-dev/sqlc/releases/tag/v1.19.0)
- `sqlc.slice` engine split: PostgreSQL uses `ANY($1::int[])` (slice passed through `pq.Array`/pgx), MySQL and SQLite use `IN (sqlc.slice('ids'))`; "Passing a nil or empty slice returns an error rather than panicking"; "This feature isn't compatible with the emit_prepared_queries configuration option". — [Retrieving rows](https://docs.sqlc.dev/en/latest/howto/select.html)
- `sqlc.embed`: added in v1.18.0 (2023-04-27) via "feat: add sqlc.embed to allow model re-use by @nickjackson in PR #1615" (PR had 78 reactions). — [v1.18.0 release](https://github.com/sqlc-dev/sqlc/releases/tag/v1.18.0); [PR #1615](https://github.com/sqlc-dev/sqlc/pull/1615)
- Embedding docs: "Embedding lets you reuse existing model structs across queries, which reduces manual serialization work"; the page documents only the basic case and lists no limitations or engine notes. — [Embedding structs](https://docs.sqlc.dev/en/latest/howto/embedding.html)
- `sqlc.embed` does not handle NULL rows from LEFT JOIN: issue #2348 (open since 2023-06-21, 51 reactions, 21 comments) reports `cannot scan null into *string`; the feature's author nickjackson wrote "Left joins were left out of the implementation because the scanning logic is not so straightforward." — [Issue #2348](https://github.com/sqlc-dev/sqlc/issues/2348); duplicates: #2997 (open, 45 reactions) and #3240 (open, 34 reactions). — [#2997](https://github.com/sqlc-dev/sqlc/issues/2997), [#3240](https://github.com/sqlc-dev/sqlc/issues/3240)
- `sqlc.embed` cannot target a CTE (#3128, open since 2024-01-12, 18 reactions, no maintainer reply), cannot return slices for one-to-many (#3144 open, 11 reactions; discussion #2643, 33 upvotes), and cannot exclude columns (#4173, open 2025-11-07). — [#3128](https://github.com/sqlc-dev/sqlc/issues/3128), [#3144](https://github.com/sqlc-dev/sqlc/issues/3144), [D#2643](https://github.com/sqlc-dev/sqlc/discussions/2643), [#4173](https://github.com/sqlc-dev/sqlc/issues/4173)
- Known `sqlc.slice` defects: SQLite queries mixing `sqlc.slice()` with other parameters break (#2452, open since 2023-07-13, 6 reactions; fix PR #4330 open since 2026-03-07), multiple identical slices in one query mishandled (#3556, open), slice plus regular parameter yields wrong placeholder ordinal (#3705, open, 7 reactions). — [#2452](https://github.com/sqlc-dev/sqlc/issues/2452), [PR #4330](https://github.com/sqlc-dev/sqlc/pull/4330), [#3556](https://github.com/sqlc-dev/sqlc/issues/3556), [#3705](https://github.com/sqlc-dev/sqlc/issues/3705)
- Known `sqlc.narg` defects: ignored with array casts (#1851, open since 2022-09-17, 9 reactions); with an overridden type plus COALESCE generates non-nullable params (#3494, open; #3900, open); `LIMIT COALESCE(sqlc.narg('limit'), 100)` fails with "unsupported reference type: <nil>" unless cast `::int` (community-found workaround in #200). — [#1851](https://github.com/sqlc-dev/sqlc/issues/1851), [#3494](https://github.com/sqlc-dev/sqlc/issues/3494), [#3900](https://github.com/sqlc-dev/sqlc/issues/3900), [#200 comment](https://github.com/sqlc-dev/sqlc/issues/200#issuecomment-1653328385)
- Comment-based "annotations" that exist today are not reuse mechanisms: boolean-flag metadata parsing (v1.20.0, #2464), `/* @sqlc-vet-disable */` (v1.20.0, #2474), parameter metadata from comments (v1.23.0, #2850), per-query rule disabling (v1.28.0, #3620). — [v1.20.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.20.0), [v1.23.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.23.0), [v1.28.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.28.0)
- A proposal to replace macros with declarative comment blocks (`/* name: ... slice: ages */`) was closed as "not planned" on 2026-04-17 with no comment. — [Issue #4343](https://github.com/sqlc-dev/sqlc/issues/4343)
- On `main` (merged 2026-07-31, not in any release as of 2026-10-19), PR #4537 by Kyle Conroy moved macro handling into a new `internal/sql/preprocess` package that rewrites `sqlc.arg/narg` to the dialect placeholder (`$1` PostgreSQL, `?` MySQL, `?1` SQLite), `sqlc.slice(name)` to a placeholder wrapped in `/*SLICE:name*/`, `sqlc.embed(table)` to `table.*`, and `@name` to a placeholder for PostgreSQL and SQLite only ("mysql: user variable, left alone"); "GoogleSQL and ClickHouse are deliberately not preprocessed." — [PR #4537](https://github.com/sqlc-dev/sqlc/pull/4537)

### Inferences
- All four macros operate strictly inside one named query; the generator has no concept of a macro that expands to SQL text written elsewhere. "Re-use" in `sqlc.embed` means re-using the generated Go struct, which only helps when you select whole tables.
- The preprocess package on `main` is the first place in sqlc's pipeline where macro text is rewritten before parsing; it is internal and not user-extensible, but it shows the maintainer is willing to treat `sqlc.*` as a textual preprocessing layer.

### Gaps
- The exact release that introduced the `@name` shorthand was not found in the release notes reviewed (v1.1.0 only mentions the `sqlc.arg('argname')` form).
- No official documentation lists `sqlc.embed` limitations (LEFT JOIN, CTE, aliases); they are only visible in issues.

## Key Question 2: Can sqlc share a SELECT list, WHERE clause, JOIN block, or CTE between queries? What happens with pasted duplicate CTE text?

### Takeaway
No. sqlc has no include, fragment, template, or shared-CTE facility; every `-- name:` block is compiled independently and duplicated text is simply compiled twice, producing duplicate `...Row` structs. The only sanctioned reuse units are database objects (tables, views, functions) and the generated model struct when a query's columns exactly match a table or view.

### Cited Findings
- Kyle Conroy's own 2019 issue #112 "Query templates" described a user asking "how it would be possible to share a set of select expressions across queries. There isn't a way to do this in the SQL standard" and proposed a `-- template:` block with `sqlc.named_author.*`; he closed it on 2021-08-17: "I haven't made any progress on this design, so I'm going to close out this issue for now." — [Issue #112](https://github.com/sqlc-dev/sqlc/issues/112)
- Issue #2244 "Feature proposal: Query Fragments" (open since 2023-04-30, 8 reactions, 12 comments) proposes `-- name: WorkspaceCheck :fragment` plus `sqlc.fragment(WorkspaceCheck)`; it has no implementation. Kyle Conroy (2023-09-26, 6 reactions): "Instead of adding a new `sqlc.xxx` function, I've been thinking about adopting the a templating system as a preprocessor step. Jinja2 supports macro definitions, which should solve your issue without us introducing any new special syntax." Nothing followed. — [Issue #2244](https://github.com/sqlc-dev/sqlc/issues/2244), [maintainer comment](https://github.com/sqlc-dev/sqlc/issues/2244#issuecomment-1735879805)
- Community statement of the status quo in #2244 (Emyrk, 2023-07-13): "The current workaround is to define it as a view, but you cannot use things such as sqlc.embed in a view." Another user (wilianto, 2024-11-18) describes keeping list/count/sum queries with ">10 where conditions" in sync by hand. — [Issue #2244](https://github.com/sqlc-dev/sqlc/issues/2244)
- Issue #2491 "Expanding sql VIEWs at generation to reuse queries (query fragments, query templates)" (open since 2023-07-21, 3 reactions, 0 comments) proposes `-- name: book_with_author :view` plus `sqlc.view(book_with_author)` so a view is expanded at generation time without being created in the database; no maintainer response. — [Issue #2491](https://github.com/sqlc-dev/sqlc/issues/2491)
- Issue #3410 "Composition for paging ?" (open since 2024-06-03, 2 reactions, 0 comments) asks to reuse one WHERE block for a list query and its COUNT query; a `CASE WHEN` in the SELECT list fails with "CASE types record and bigint cannot be matched". — [Issue #3410](https://github.com/sqlc-dev/sqlc/issues/3410)
- Duplicate SELECT lists produce distinct row types: "Queries that select the same columns each get their own row struct (`GetBookRow`, `ListBooksByAuthorRow`, …) even when the structs are identical, so callers end up converting between them"; the same PR notes "An explicit `:type` wins over the existing reuse of a table's model when the columns happen to match one." - CTE support exists but is per-query and buggy. Fixes shipped: "Check delete statements for CTEs" (v1.12.0), SQLite "find relation from WITH clause" (v1.20.0), "Support subqueries in the FROM clause" (v1.27.0), recursive-CTE star expansion #1219 (closed 2023-10-24), CTE-in-CTE #2004 (closed 2023-10-25). — [v1.12.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.12.0), [v1.20.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.20.0), [v1.27.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.27.0), [#1219](https://github.com/sqlc-dev/sqlc/issues/1219), [#2004](https://github.com/sqlc-dev/sqlc/issues/2004)

- Dynamic/optional JOINs have no answer either: discussion #3594 "sqlc support for query with conditional/optional join" (2024-09-10, 2 upvotes, 0 comments). — [D#3594](https://github.com/sqlc-dev/sqlc/discussions/3594)
- The Go codegen exposes query text as unexported `const` strings; `emit_exported_queries` "lets other packages access generated SQL statements" and `emit_sql_as_comment` (v1.25.0) places the SQL in a comment, but neither feeds SQL back into sqlc. — [Configuration](https://docs.sqlc.dev/en/latest/reference/config.html), [v1.25.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.25.0)

### Inferences
- Pasting the same CTE into several queries is legal and common; the cost is purely maintenance plus duplicate `Row` types, and each copy independently hits the CTE resolver bugs above (especially the #3585 alias bug when `sqlc.arg` is used inside or against a CTE).
- Because row-struct reuse only happens on an exact column match with a table or view, defining a VIEW for the shared projection is the only way today to get one shared Go type across several queries.

### Gaps
- No official document states the rule for when a query reuses a table/view model struct instead of a `Row` struct; the rule is only described in PR #4630's text and observable behavior.

## Key Question 3: Views, materialized views, and schema-defined SQL functions: type inference, nullability, known bugs, and whether they are the sanctioned reuse path

### Takeaway
sqlc registers a VIEW as a catalog table whose columns are computed from the view's SELECT, so views are the de facto way to share a projection or a JOIN, and the community relies on them (including as a workaround for nullable `sqlc.embed`). No official doc recommends views or functions for reuse, materialized views still have open parsing bugs, and PostgreSQL functions returning TABLE only type correctly with the database-backed analyzer; MySQL functions/procedures were unparseable for years.

### Cited Findings
- VIEW support landed in v1.9.0 (2021-08-13, PR #1044); materialized views in v1.13.0 (2022-04-03, PR #1509); `COMMENT ON VIEW` and `REFRESH MATERIALIZED VIEW` parsing in v1.19.0; `ALTER VIEW ... SET SCHEMA` in v1.23.0; renaming/dropping materialized views in v1.28.0 (PR #3728). — [v1.9.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.9.0), [v1.13.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.13.0), [v1.19.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.19.0), [v1.23.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.23.0), [v1.28.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.28.0)
- Implementation (v1.31.1 source): `Catalog.createView` calls `colGen.OutputColumns(stmt.Query)` and appends a `Table{Rel: ..., Columns: cols}` to the schema; `CREATE OR REPLACE` replaces the existing entry. Views are therefore tables to the rest of the compiler, with column types and nullability inferred from the view's SELECT by the same output-column logic used for queries. — [internal/sql/catalog/view.go @ v1.31.1](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/catalog/view.go)
- The "Modifying the database schema" how-to only documents `CREATE TABLE`/`ALTER TABLE` and migration-tool markers (atlas, dbmate, golang-migrate, goose, sql-migrate, tern); it says nothing about views or functions. — [DDL how-to](https://docs.sqlc.dev/en/latest/howto/ddl.html)
- Views are used as the community's standard workaround for nullable embeds: "if you add a view with just your LEFT JOIN, you can JOIN it and sqlc will generate the model with all nullable fields" (hectorj-thetreep, 2023-10-11, 8 reactions), and a generic per-table form `CREATE VIEW images_vw AS SELECT images.* FROM (SELECT NULL WHERE FALSE) dummy FULL JOIN images ON TRUE;` whose "explain analyze output looks the same" (Jonathan-Landeed, 2025-02-12). — [#2348 comment](https://github.com/sqlc-dev/sqlc/issues/2348#issuecomment-1757903348), [#2348 comment](https://github.com/sqlc-dev/sqlc/issues/2348#issuecomment-2652338961)
- The view workaround's cost: "I just wish it didn't introduce a model with all nullable fields in our domain" (kevlarr, 10 reactions); "The view models still need to be mapped back to the source models" (ErikKalkoken, #2997). — [#2348 comment](https://github.com/sqlc-dev/sqlc/issues/2348#issuecomment-1802333906), [#2997 comment](https://github.com/sqlc-dev/sqlc/issues/2997#issuecomment-2079127438)
- Open view/matview bugs: #4262 "SQLC does not infer nullability for subqueries in view SELECT" (open 2026-01-14), #2300 "simple migration with materialized view cannot be parsed" (open since 2023-06-07), #3371 "Renaming a materialized view causes sqlc generate to fail" (open since 2024-05-09, despite the v1.28.0 fix), #3403 `pg_matviews` missing from the built-in catalog (open). Closed: #1545 "Materialized View does not enforce columns names" (closed 2023-10-24), #464 (2020), #1021 (2022), #1519 (2023). — [#4262](https://github.com/sqlc-dev/sqlc/issues/4262), [#2300](https://github.com/sqlc-dev/sqlc/issues/2300), [#3371](https://github.com/sqlc-dev/sqlc/issues/3371), [#3403](https://github.com/sqlc-dev/sqlc/issues/3403), [#1545](https://github.com/sqlc-dev/sqlc/issues/1545)
- `pg_tables` and `pg_views` were added to the built-in PostgreSQL catalog in v1.16.0; `information_schema` was implemented in the same release. — [v1.16.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.16.0)
- PostgreSQL functions: v1.5.0 generated signatures "for all built-in functions" and popular extensions; v1.4.0 "Support functions with table parameters"; v1.6.0 "variadic stored procedures and functions"; v1.19.0 "Allow use of table and column aliases for table functions returning unknown types"; v1.23.0 "Support functions with OUT params". `strict_function_checks` (default `false`) controls whether calling an unknown function is an error. — [v1.5.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.5.0), [v1.4.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.4.0), [v1.6.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.6.0), [v1.19.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.19.0), [v1.23.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.23.0), [Configuration](https://docs.sqlc.dev/en/latest/reference/config.html)
- Functions `RETURNS TABLE (...)` (#1322) were only fixed "in v1.23.0 by enabling the database-backed query analyzer" (Kyle Conroy, 2023-10-24); a 2025-04-09 follow-up shows anonymous multi-column table returns "still return interface{}" without it. The database-backed analyzer "currently supports PostgreSQL, with MySQL and SQLite support planned". — [#1322 comment](https://github.com/sqlc-dev/sqlc/issues/1322#issuecomment-1778209937), [#1322 comment](https://github.com/sqlc-dev/sqlc/issues/1322#issuecomment-2789124198), [v1.23.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.23.0)
- MySQL: "MySQL engine doesn't support: CREATE TRIGGER, CREATE FUNCTION, CREATE PROCEDURE" (#1403, opened 2022-01-30, labelled `upstream` because of the TiDB/pingcap parser; closed as completed on 2026-08-21 without an explanatory comment); the reporter's workaround was to "preprocess my migration files and use a script to filter out" those statements. v1.21.0 added parsing of `CALL` so stored procedures became usable with MySQL. — [#1403](https://github.com/sqlc-dev/sqlc/issues/1403), [v1.21.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.21.0)
- SQLite: only "sqlite stdlib functions" are modelled (v1.15.0); SQLite has no user-defined SQL functions in DDL. — [v1.15.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.15.0)
- Community pushback on functions as a reuse mechanism (Emyrk, #2244, 2024-11-04): "a function is still much heavier than what is requested. A function requires a migration, and mutating that function requires a REPLACE the old function. At present, all queries are generated client side, so making changes is trivial and does not require changing the DB schema." — [#2244 comment](https://github.com/sqlc-dev/sqlc/issues/2244#issuecomment-2455623798)
- Type-inference quality in general: the maintainer's 2026 roadmap states "The largest source of bugs today is sqlc's homegrown query analysis engine... it's difficult to faithfully replicate the behavior of PostgreSQL, MySQL and SQLite. It results in a constant stream of issues when the query analysis is incorrect." — [D#4204](https://github.com/sqlc-dev/sqlc/discussions/4204)

### Inferences
- Views are the only reuse mechanism that is both supported by the compiler and gives a shared Go type, but they push the abstraction into the database schema and migrations, flatten nullability (every column of a LEFT-JOIN view becomes nullable), and are subject to the same inference bugs as queries.
- Nothing from the maintainers endorses views or functions as "the" way to share query logic; the only maintainer-articulated direction for text reuse is the never-built templating preprocessor.

### Gaps
- Could not find a maintainer statement on how view column nullability should be computed; the behavior is inferred from source and from the #2348 workaround reports.
- The reason #1403 was closed in August 2026 (fixed by the new `marino` MySQL parser on `main`, or triage) is not stated in the thread.

## Key Question 4: Issues, discussions, and PRs for fragments, macros, includes, templates, composable/dynamic queries, with maintainer positions

### Takeaway
Dynamic queries are sqlc's longest-running and most-upvoted request (discussion #364 since Feb 2020, 124 upvotes; issue #3414, 54 reactions). Maintainers have never said "no", but every one of seven implementation PRs was closed unmerged, the last maintainer comment on the topic (Aug 2025) says the syntax is undecided, and the November 2025 roadmap omits dynamic queries entirely.

Discussions

## Key Question 5: Preprocessing hooks, include directives, templates, pre-generate steps; `queries:` paths; generated .sql as input

### Takeaway
sqlc has no user-facing preprocessing hook, include directive, or template step; plugins are codegen-only. The `queries:` key accepts a file, a directory (non-recursive, `.sql` only, hidden files and down migrations skipped), a list of such paths, and since v1.24.0 glob patterns. Nothing in the docs discourages generated `.sql` input, and the new `sqlc parse` (v1.31.0) plus `sqlc analyze`/`sqlc fmt` (main only) are the first official building blocks an external preprocessor could reuse.

### Cited Findings
- Configuration reference: `queries`: "Directory of SQL queries or path to single SQL file; or a list of paths."; `schema`: "Directory of SQL migrations or path to single SQL file; or a list of paths." Globs are not mentioned on the page. — [Configuration](https://docs.sqlc.dev/en/latest/reference/config.html)
- Lists of paths have been accepted since v1.2.0 (2020-04-07, PR #426). — [v1.2.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.2.0)
- Glob support: PR #2955 "Enhance sqlpath.Glob to actually support glob wildcard" merged 2023-11-14 by kyleconroy ("I only call filepath.Glob if the path contains `?*[]`... This will be released in 1.24.0"). — [PR #2955](https://github.com/sqlc-dev/sqlc/pull/2955)
- v1.31.1 source of the path reader: "Only includes files ending in .sql. Omits hidden files, directories, and down migrations."; a directory is read with `os.ReadDir` (one level, not recursive); patterns containing `*?[]` go through `filepath.Glob`; files whose base name starts with `.` and files recognised by `migrations.IsDown` are skipped. — [internal/sql/sqlpath/read.go @ v1.31.1](https://github.com/sqlc-dev/sqlc/blob/v1.31.1/internal/sql/sqlpath/read.go)
- Users confirmed lists work but "It doesn't support glob patterns though, right?" remained unanswered in #2816 (2025-05-19), reflecting the docs gap. — [#2816](https://github.com/sqlc-dev/sqlc/issues/2816)
- Plugins: the plugin guide only shows plugins under `codegen` (`out` + `plugin`), WASM plugins are "fully sandboxed; they do not have access to the network, filesystem, or environment variables", process plugins "offer minimal security"; the page says nothing about plugins preprocessing or rewriting queries. — [Using plugins](https://docs.sqlc.dev/en/latest/guides/plugins.html)
- Plugin history: process-based codegen plugins v1.14.0, WASM codegen plugins v1.15.0, env-var passthrough v1.21.0, gRPC-style plugin interface refactor "to better support future functionality" v1.24.0, wazero runtime v1.25.0, JSON format for process plugins v1.29.0. — [v1.14.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.14.0), [v1.15.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.15.0), [v1.21.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.21.0), [v1.24.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.24.0), [v1.25.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.25.0), [v1.29.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.29.0)
- The only maintainer mention of a preprocessing step is the 2023-09-26 Jinja2 idea in #2244 (never implemented). — [#2244 comment](https://github.com/sqlc-dev/sqlc/issues/2244#issuecomment-1735879805)
- Community plugin `vtuanjs/sqlc-gen-go` implements `emit_dynamic_filter` via `--:if`-style annotations as a codegen plugin, i.e. after sqlc's analysis (2026-04-04). — [D#364 comment](https://github.com/sqlc-dev/sqlc/discussions/364#discussioncomment-16447398)
- Community plugin `sqlc-gen-from-template` was linked from the docs in v1.28.0 (PR #3601); it templates generated code, not SQL. — [v1.28.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.28.0)
- `sqlc parse` (released in v1.31.0 via "Add parse subcommand with AST JSON output (#4240)" and "Graduate parsecmd experiment (#4253)"): "parses SQL from a file or standard input and prints the abstract syntax tree (AST) as one JSON document. It needs no configuration file or database connection"; output is one object per statement with `name`, `cmd`, `ast`; `tag: TODO` marks untranslated clauses; marked beta. The latest docs list dialects postgresql, mysql, sqlite, clickhouse, googlesql, mssql, duckdb, but v1.31.0 only added ClickHouse (#4267); the others are `main`-only. — [parse docs](https://docs.sqlc.dev/en/latest/howto/parse.html), [v1.31.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.31.0)
- `sqlc analyze` (docs latest, not in any release): prints inferred result `columns` (name, type, table, nullable) and `params` per query "directly from the schema using sqlc's native static analysis", "does not require a configuration file and does not connect to a database"; `--ast` adds the AST; "analyze can report types differently from generate". — [analyze docs](https://docs.sqlc.dev/en/latest/howto/analyze.html)
- `sqlc fmt` (docs latest, not in any release): "rewrites the query files referenced by your sqlc configuration into a canonical format" by printing from the AST, in place unless `--diff`; PostgreSQL, MySQL, SQLite; beta. — [fmt docs](https://docs.sqlc.dev/en/latest/howto/fmt.html)
- v1.31.0 also shipped `sqlfile.Split` (#4146), "comprehensive SQL AST formatting" (#4205), a "star expander for SELECT * and RETURNING * (PostgreSQL, MySQL, SQLite)" (#4203), an `SQLCEXPERIMENT` env var (#4228), and a PostgreSQL "analyzerv2 experiment for database-only analysis" (#4237). — [v1.31.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.31.0)
- `SQLCEXPERIMENT` on latest docs defines one experiment, `coreanalyzer`, which "routes sqlc generate through the core catalog and analyzer instead of each engine's own analysis path"; `SQLCDEBUG=dumpast=1` prints the generic AST and `dumpcatalog=1` the catalog. — [Environment variables](https://docs.sqlc.dev/en/latest/reference/environment-variables.html)
- A "first-class Go API, similar to how esbuild does it" is planned (roadmap, 2025-11-30) but unreleased; PR #4418 "Extract code generation logic into internal/api package" has been open since 2026-04-28. — [D#4204](https://github.com/sqlc-dev/sqlc/discussions/4204), [PR #4418](https://github.com/sqlc-dev/sqlc/pull/4418)
- Generated SQL as input: sqlc "doesn't run migrations. It only reads the SQL files" and ignores down migrations. No documentation discourages generated query files; the only related caveat is that `sqlc fmt` rewrites configured query files in place. — [DDL how-to](https://docs.sqlc.dev/en/latest/howto/ddl.html), [fmt docs](https://docs.sqlc.dev/en/latest/howto/fmt.html)
- Official sqlc-dev organization repositories contain no fragment/template/dynamic-query tool: sqlc, sqlc-gen-go, sqlc-gen-python, sqlc-gen-kotlin, sqlc-gen-typescript, sqlc-gen-greeter, sqlc-gen-test, plugin-sdk-go, quickdb, and the new parser repos (oliphant, marino, meyer, teesql, zetajones, doubleclick, darkwing). — [sqlc-dev org](https://github.com/orgs/sqlc-dev/repositories)

### Inferences
- An external "pre-generate" tool that expands fragments into plain `.sql` files placed in a configured directory (or matched by a glob) is fully within supported behavior; sqlc will treat the output exactly like hand-written queries, including `vet`/`verify`.
- `sqlc parse` is the only released, engine-neutral way to obtain sqlc's own AST for a query from outside the binary; `analyze` would add column/param typing but is unreleased.

### Gaps
- No documentation states whether directories are read recursively; the non-recursive behavior is established only from the v1.31.1 source.
- Release version for `sqlc analyze` and `sqlc fmt` is unknown (absent from v1.31.0 and v1.31.1 notes).

## Key Question 6: Documented optional-filter patterns (sqlc.narg + IS NULL OR, CASE WHEN) and their limitations and performance implications

### Takeaway
The official docs show `sqlc.narg` only with `coalesce(sqlc.narg('name'), name)` for partial UPDATEs and `CASE WHEN` for conditional values; the `(col = sqlc.narg('x') OR sqlc.narg('x') IS NULL)` filter pattern and the `CASE WHEN @flag::bool THEN ... ELSE TRUE END` pattern come from maintainer comments in issue #200 and discussion #364. Both are acknowledged by the maintainers to degrade plans (worst-case planning, no index use in ORDER BY CASE), to scale badly beyond a few parameters, and to have engine-specific pitfalls on MySQL and SQLite.

### Cited Findings
- Documented examples: `UpdateAuthor` uses `coalesce(sqlc.narg('name'), name)` and `coalesce(sqlc.narg('bio'), bio)` producing `sql.NullString` params; `UpsertAuthorName` uses `CASE WHEN` on a boolean parameter; the page contains no `IS NULL OR` example and no `CASE WHEN` filter example. — [Naming parameters](https://docs.sqlc.dev/en/latest/howto/named_parameters.html)
- Maintainer-endorsed `IS NULL OR` form (Kyle Conroy, 2022-06-12, 16 reactions): `WHERE (name = sqlc.narg('name') OR sqlc.narg('name') IS NULL)`. The original `($1 IS NULL OR name = $1)` ordering failed with `unsupported reference type: <nil>` because the first use has no type context. — [#200](https://github.com/sqlc-dev/sqlc/issues/200), [comment](https://github.com/sqlc-dev/sqlc/issues/200#issuecomment-1153232389)
- Maintainer-endorsed `CASE WHEN` form (Kyle Conroy, 2020-03-01): `AND (CASE WHEN @is_bar::bool THEN bar = @bar ELSE TRUE END)` with `ORDER BY CASE WHEN @bar_asc::bool THEN bar END asc, ...`. — [D#364 comment](https://github.com/sqlc-dev/sqlc/discussions/364#discussioncomment-55082)
- Boolean-flag form from #200 (danielbprice, 2022-03-07, 8 reactions): `(NOT sqlc.arg('HasCreatedFrom')::bool OR (created >= sqlc.arg('CreatedFrom')))`, "icky in my personal opinion". — [#200 comment](https://github.com/sqlc-dev/sqlc/issues/200#issuecomment-1060256304)
- Real-world use at scale: Coder's `workspaces.sql` uses `CASE WHEN` blocks to avoid duplicating queries with different WHERE cases (cited by Emyrk in #2244). — [coder/coder workspaces.sql](https://github.com/coder/coder/blob/6914862903b9ac4dd20629862c92806e2f8f8128/coderd/database/queries/workspaces.sql#L232-L237)
- Performance, maintainer-acknowledged: Kyle Conroy 2020-08-23: "You can write queries that filter on different parameters but those queries may perform poorly in production." — [D#580](https://github.com/sqlc-dev/sqlc/discussions/580#discussioncomment-55097); Andrew Benton 2023-09-14: the CASE approach "only really works for a small number of parameters". — [D#364](https://github.com/sqlc-dev/sqlc/discussions/364#discussioncomment-7004672)
- Performance, community evidence: "static query with dynamic filtering is generally regarded as one of the worst performance anti-pattern for RDBMS... the query planner can't optimize the query and has to prepare for the worst case (all filters are unused) and will decide for a seq_scan in all cases (no indexes will be used)" (arddor, 2020-03-02, 12 upvotes; Kyle thanked him for "the great write up about why this pattern can result in sub-optimal query plans"); "the benchmarks showed considerable impact on query performance" (mehdijoafshani, 2020-03-02, 17 upvotes); "ordering with a case statement will not be able to use the indexes" (ovadbar, 2023-10-09); "We hit the same wall... we dropped it once queries stopped using indexes the way we wanted" (devfros, 2026-06-02); "the postgres query-planner... preferring a sequential scan just because it did not read the value of the param" (celso-alexandre, 2026-05-27). — [D#364](https://github.com/sqlc-dev/sqlc/discussions/364)
- Type pitfalls: `ORDER BY CASE` across differently typed columns fails with `CASE types text and integer cannot be matched (SQLSTATE 42804)`; the fix is one CASE pair per type/direction. — [#830](https://github.com/sqlc-dev/sqlc/issues/830), [D#364 comment](https://github.com/sqlc-dev/sqlc/discussions/364#discussioncomment-7609386)
- Codegen pitfalls: using the same `sqlc.narg('name')` twice with `query_parameter_limit` > 1 generates `func ListUsers(ctx, name *string, name *string)` ("name redeclared in this block") on v1.30.0 with MySQL; with the default limit of 1 a params struct is emitted and it works (#4191, open since 2025-11-21; also reported in #200 on 2025-11-21). — [#4191](https://github.com/sqlc-dev/sqlc/issues/4191), [#200 comment](https://github.com/sqlc-dev/sqlc/issues/200#issuecomment-3562335832)
- `LIMIT COALESCE(sqlc.narg('limit_val'), 100)` errors with `unsupported reference type: <nil>` unless written `sqlc.narg('limit_val')::int` (PostgreSQL); `sqlc.arg`/`@` in LIMIT/OFFSET has its own open issue (#3840, 9 reactions). — [#200 comment](https://github.com/sqlc-dev/sqlc/issues/200#issuecomment-1653328385), [#3840](https://github.com/sqlc-dev/sqlc/issues/3840)
- MySQL specifics: `@name` is unsupported; `WHERE (CASE WHEN ? THEN status IN (?) ELSE TRUE END)` fails with `unsupported reference type: < nil >` yet exits 0 (2022-08-09); the working form is `(CASE WHEN sqlc.arg(is_name) THEN name = sqlc.arg(name) ELSE TRUE END)` without `::bool` (2025-03-14); `IF(?, status IN (?), 1)` and `(status IN (?) OR ?)` were suggested; `version = ifnull(sqlc.arg('version'), version)` yields an `interface{}` param. — [D#364](https://github.com/sqlc-dev/sqlc/discussions/364), [Naming parameters](https://docs.sqlc.dev/en/latest/howto/named_parameters.html)
- SQLite specifics: `sqlc.narg` did not work on SQLite until v1.19.0 (#1881 closed 2023-06-06); `sqlc.slice` still conflicts with other parameters (#2452 open). — [#1881](https://github.com/sqlc-dev/sqlc/issues/1881), [#2452](https://github.com/sqlc-dev/sqlc/issues/2452)
- Official tooling to detect the plan regressions: `sqlc vet` gained `EXPLAIN` output in the CEL environment in v1.20.0 (`postgresql.explain`, `mysql.explain`, database connection required), and the blog post "Prevent full table scans in production" (2023-11-30) describes using it; the `sqlc/db-prepare` rule prepares each query against a live database. — [vet docs](https://docs.sqlc.dev/en/latest/howto/vet.html), [v1.20.0](https://github.com/sqlc-dev/sqlc/releases/tag/v1.20.0), [blog index](https://sqlc.dev/posts/)
- A compiled Go-side alternative recommended inside the sqlc community: wrapping sqlc's `DBTX` with a Squirrel-built query ("intercepts the DB layer to replace static queries while keeping sqlc's models intact", yiplee, 2025-12-15); `projectdiscovery/sqlc-go-builder` rewrites the MySQL AST with the Vitess parser (2023-05-08, 8 upvotes); a list of "hacks" blog (fira42073, 2025-12-13). — [D#364](https://github.com/sqlc-dev/sqlc/discussions/364)

### Inferences
- The maintainers treat the `CASE WHEN`/`IS NULL OR` patterns as the official workaround while conceding their cost; the strongest technical argument against them (worst-case planning, index loss) is exactly what PR #4485's compile-time expansion is designed to avoid.
- Any library that generates one static query per filter combination removes the planner problem but reintroduces the combinatorial-explosion problem (noted in #3414: "Now you end up with dozens of functions as your filters grow").

### Gaps
- No official benchmark or maintainer-published measurement of the CASE/IS NULL pattern's plan impact exists; all performance claims are user reports.
