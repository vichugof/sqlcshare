# Go alternatives to sqlc for query re-use and composition: comparison (state as of 2026-10-19)

Scope: Go SQL code generators, query builders, template engines and SQL-file loaders, compared with sqlc on re-use, compile-time type safety, runtime overhead, engine support, maintenance, license and interoperability with sqlc-generated code. All repository metrics (stars, open issues, last push, release dates) were read from the GitHub REST API on 2026-10-19 unless stated otherwise; `open_issues` from that API counts issues plus open pull requests. Anything not backed by a fetched page is marked UNVERIFIED.

## Key Question 1: Per-library comparison (approach, re-use mechanism, type safety, runtime overhead, engines, maintenance, license, sqlc interop)

### Takeaway
No library combines sqlc's "write plain SQL in .sql files, get typed Go" model with first-class fragment sharing. The closest is Bob's query generation (added April 2025, composable `With()` added June 2026), which parses `.sql` query files like sqlc but emits query objects that can be used as a base and extended with builder mods; it does not offer named reusable fragments inside the SQL files. Everything else either keeps SQL text but drops static checking (sqlx, dotsql, goyesql, sqlt, tqla, pgx NamedArgs), or offers composition through a Go DSL that replaces SQL text (jet, Bob builder, sq, goqu, squirrel, go-sqlbuilder, sqlingo, Bun, ent, GORM).

#### stephenafamo/bob (query builder + ORM generator + sqlc-style query generation)
- Approach: "Query builder (Layer 1)", "SQL executor", "Models", "Code generation of Models and Factories from your database schema", and "Code generation of Queries similar to sqlc". Layer 4 is headed "similar to sqlc" and says: "I believe this is the final peice of the puzzle, and extends the type-safety to hand-crafted SQL queries." Supported: PostgreSQL, MySQL/MariaDB, SQLite, with Queries, Models, ORM Gen, Factory Gen and Query Gen all marked supported for each. MIT. — [Bob README](https://github.com/stephenafamo/bob)
- Query generation from SQL files: "This is similar to sqlc." You write SQL in `.sql` files and point the driver at the folder via the `queries` config option; for each file Bob generates `file_name.bob.go` and `file_name.bob_test.go`. Each query starts with a comment naming it (`-- AllUsers`); optional annotations `result_type_one`, `result_type_all`, `transformer`; columns/params accept `name`, `type`, `nullable`, any of which can be omitted and inferred. `SELECT *` is expanded to explicit columns. Related-data column naming (`related_table__column_name` to-one, `related_table.column_name` to-many) makes `All()` nest rows. — [Bob docs: Queries](https://bob.stephenafamo.com/docs/code-generation/queries)
- Composability of generated queries (the key sqlc difference): "The generated query is a `orm.ModQuery` object, which can also be used as a [`QueryMod`]." and "This opens up many use cases, since you can use the generated query as a base and add more mods to it." `With()` applies extra mods and returns a runnable query: `sm.Where` is ANDed to an existing WHERE, `sm.OrderBy` appended, `sm.Limit`/`sm.Offset` replace existing values; for PostgreSQL UNION/INTERSECT/EXCEPT there are `sm.OrderCombined`, `sm.LimitCombined`, `sm.OffsetCombined`, `sm.FetchCombined`. Limitations: SQLite has no combined-clause mods; in MySQL adding ORDER BY/LIMIT/OFFSET via `With()` to a query that already defines them can produce invalid SQL. The page does not mention using generated queries as subqueries or CTEs. — [Bob docs: Queries](https://bob.stephenafamo.com/docs/code-generation/queries)
- Result typing: `result_type_one`/`result_type_all` are described as "used to generate the result type"; the example annotation is `-- AllUsers *models.User:models.UserSlice:bob.SliceTransformer[ONETYPE, ALLTYPE]` and the transformer section says "If manually set the `result_type` will not be generated." Generated finishers: `One(ctx, db)`, `All(ctx, db)`, `Cursor(ctx, db)`. Nullable columns use `null.Val[...]`. — [Bob docs: Queries](https://bob.stephenafamo.com/docs/code-generation/queries)
- Timeline from CHANGELOG: v0.26.0 (2024-05-21) "Add `bobgen-sql` a code generation driver for SQL schema files. Supports PostgreSQL and SQLite."; v0.30.0 (2025-01-16) `QueryFolders` added to `gen/drivers.DBInfo`; v0.32.0 (2025-04-24) "Added templates for query generation", "Implement the Postgres query parser for `SELECT` statements", "Implement the SQLite query parser for `SELECT` statements", `queries` key added to `bobgen-sql`/`bobgen-sqlite` config, `orm.ModQuery`/`orm.ModExecQuery` types added; v0.35.0 (2025-05-26) INSERT/UPDATE/DELETE query generation for SQLite and "Add support for MySQL to `bobgen-sql`"; v0.39.0 (2025-07-28) `All` returns nested structs; v0.40.0 (2025-08-13) plugin outputs include `where` ("Generates type-safe code for `WHERE` clauses in queries") and `queries`; v0.43.0 (2026-04-29) "customizable MySQL and PostgreSQL driver image setting for `bobgen-sql`"; v0.46.0 (2026-06-11) "`With()` on generated queries as a more ergonomic method to add mods on top of generated queries"; v0.48.0 (2026-06-26) fix for CTE parsing with table functions; v0.49.0 (2026-07-20) "Code generation now emits a reflection-free `scan.Mapper` per table ... scans without the per-row reflection of `scan.StructMapper`"; v0.50.0 (2026-08-11) fix for repeated `$N` parameters being renumbered as distinct args in generated query mods. — [Bob CHANGELOG](https://github.com/stephenafamo/bob/blob/main/CHANGELOG.md)
- Parser dependencies in `go.mod`: `github.com/pganalyze/pg_query_go/v6 v6.1.0`, `github.com/antlr4-go/antlr/v4 v4.13.1`, `github.com/stephenafamo/sqlparser` (pseudo-version dated 2026-01-22), plus `testcontainers-go/modules/mysql`. — [Bob go.mod](https://github.com/stephenafamo/bob/blob/main/go.mod)
- Builder composition model: "QueryMods are options applied to a query. Each query type of each dialect defines what mods can be applied to it." Conditional mods via `Apply()`; because mods mutate the query object, reuse of a base query requires `Clone()`. A query stored in a variable can be used as a CTE (`sm.With("adults").As(cte)`). Raw SQL "Either at the top level with `psql.RawQuery()` or inside any clause with `psql.Raw()`", using `?` placeholders rendered as `$1, $2...`. — [Bob docs: Building queries](https://bob.stephenafamo.com/docs/query-builder/building-queries)
- Executor interface: `type Executor interface { QueryContext(ctx, query string, args ...any) (scan.Rows, error); ExecContext(context.Context, string, ...any) (sql.Result, error) }`; `bob.NewDB(db *sql.DB)` "wraps an [*sql.DB] ... This is useful when an existing *sql.DB is used in other places in the codebase". — [Bob source via GitHub code search](https://github.com/stephenafamo/bob/blob/main/stdlib.go)
- Bob-vs-Jet page: "Jet is purposefully **NOT AN ORM**", "since Jet is only query builder, every query has to be built and mapped manually"; Bob's comparison pages cover GORM, Ent, SQLBoiler and Jet, not sqlc. — [Bob vs Jet](https://bob.stephenafamo.com/vs/jet/)
- Bob's builder-intro claims "Faster than comparable packages" and links to the author's own benchmark repo (see KQ3). — [Bob query-builder intro](https://bob.stephenafamo.com/docs/query-builder/intro)

#### go-jet/jet (schema codegen + Go SQL DSL)
- Approach: generator reads the database schema and produces SQL-builder packages and model types; queries are written in Go with dot-imports; "is not an ORM". Supports PostgreSQL, MySQL, SQLite; CockroachDB and MariaDB tested. Type safety: every column has a type, string columns compare only with string expressions, etc.; renaming/removing a column breaks the build after regeneration. Features include sub-queries, UNION/INTERSECT/EXCEPT, WINDOW, WITH. Go 1.24+; module `github.com/go-jet/jet/v2`; `SELECT_JSON` needs v2.13.0+ (released 2025-03-16 per GitHub release). Apache-2.0. — [jet README](https://github.com/go-jet/jet)
- Result mapping uses reflection: "`Query` uses reflection to introspect destination type structure"; rows are grouped by primary key and "Every new destination struct object is cached by his and all the parents primary key"; "Go struct field has to be public for scan to work"; Strict Scan (`qrm.GlobalConfig.StrictScan = true`, v2.13.0+) panics on unmapped columns. — [jet wiki: QRM](https://github.com/go-jet/jet/wiki/Query-Result-Mapping-(QRM))
- Raw SQL escape hatches: "Raw Statement Fallback: With the loss of all Jet benefits, the entire statement can also be written as a raw query"; also a "Raw Expression Fallback"; FAQ entries exist for "How to construct dynamic projection list?", "How to construct dynamic condition?", and dynamic IN lists. — [jet wiki: FAQ](https://github.com/go-jet/jet/wiki/FAQ)
- Executor interface (`qrm.DB`): `Exec`, `ExecContext`, `Query`, `QueryContext` returning `*sql.Rows`/`sql.Result` (so `*sql.DB` and `*sql.Tx` satisfy it). — [jet qrm/db.go](https://github.com/go-jet/jet/blob/master/qrm/db.go)
- v2.16.1 (2026-10-06) release notes: fixes for MySQL literal escaping and "type wrappers mutating wrapped expressions, preventing data races and unintended cross-query side effects". — [jet releases](https://github.com/go-jet/jet/releases)

#### jschaf/pggen (sqlc-like codegen, Postgres only)
- Approach: named queries with `:one`/`:many`/`:exec` and `pggen.arg('name')`; "pggen gets the same type information by running the queries on Postgres" (reads `pg_type`, `pg_class`, `pg_attribute`). "pggen was directly inspired by sqlc." Recommends sqlc "if you don't wish to run Postgres to generate code" or need better nullability analysis. Postgres only. Generates a `Querier` interface with per-query direct, `Batch` and `Scan` methods, `<Query>Row` structs, `<Query>Params` for 3+ params. MIT. No statement of archival or maintenance mode in the README. — [pggen README](https://github.com/jschaf/pggen)
- Dependencies: `go 1.24.1`, `github.com/jackc/pgx/v4 v4.18.3`, `github.com/jackc/pgtype v1.14.4` (pgx v4, not v5). — [pggen go.mod](https://github.com/jschaf/pggen/blob/main/go.mod)
- No query re-use/composition features are described. — [pggen README](https://github.com/jschaf/pggen)

#### xo/xo, now xo/dbtpl (template-driven codegen from schema or custom query)
- "`dbtpl` is a command-line tool to inspect and generate templated code based on a database schema or a custom database query." Schema mode connects to the DB and applies Go templates; "In query mode, `dbtpl` parses your query to generate code from Go templates. It finds related tables in your database to ensure type safety." Supports PostgreSQL, MySQL, Oracle, Microsoft SQL Server, SQLite3 (models, PKs, FKs, indexes, stored procs). Note in README: "it is not the goal, nor the intention for dbtpl to be a 'silver bullet,' nor to completely eliminate the manual authoring of SQL / Go code." — [dbtpl README](https://github.com/xo/dbtpl)
- No fragment/re-use mechanism beyond custom templates is described. — [dbtpl README](https://github.com/xo/dbtpl)

#### doug-martin/goqu (runtime builder)
- "expressive SQL builder and executor"; goal "Create an expressive DSL that would find common errors with SQL at compile time"; not an ORM. Dialects: mysql, postgres, sqlite3, sqlserver. Column names are strings (`goqu.Ex`, `goqu.Record` maps, `db:` tags). `Prepared(true)` for placeholder interpolation. MIT. — [goqu README](https://github.com/doug-martin/goqu)
- CTEs: "To use CTEs in `SELECT` statements you can use the `With` method." (also with INSERT/UPDATE/DELETE datasets). — [goqu docs/selecting.md](https://github.com/doug-martin/goqu/blob/master/docs/selecting.md)

#### Masterminds/squirrel (runtime builder)
- "Squirrel is 'complete'. Bug fixes will still be merged (slowly)." Stability badge: Maintenance. "Squirrel helps you build SQL queries from composable parts" (example: `users := sq.Select("*").From("users")...; active := users.Where(sq.Eq{"deleted_at": nil})`). "Squirrel is not an ORM." — [squirrel README](https://github.com/Masterminds/squirrel)
- Runner interfaces: `BaseRunner` (Exec, Query), `Runner` (+QueryRow), `StdSql`, and context variants `StdSqlCtx` (`QueryContext`, `QueryRowContext`, `ExecContext`), so `*sql.DB` satisfies them directly. — [squirrel.go](https://github.com/Masterminds/squirrel/blob/master/squirrel.go), [squirrel_ctx.go](https://github.com/Masterminds/squirrel/blob/master/squirrel_ctx.go)

#### huandu/go-sqlbuilder (runtime string builder + reflection "Struct" ORM)
- "A flexible and powerful SQL string builder library plus a zero-config ORM." It generates SQL and args but never calls `database/sql`. Flavors: MySQL (default), PostgreSQL, SQLite, SQLServer, CQL, ClickHouse, Presto, Oracle, Informix. Re-use: `Clone()` on eight builders so a base builder is an immutable template; `BuilderAs` nests builders as subqueries/JOIN sources; `WhereClause` can be shared between builders (e.g. SELECT to UPDATE); `SQL(...)`, `Buildf`, `Build`, `BuildNamed` for freestyle fragments; `CTEBuilder`/`CTEQueryBuilder`; `Struct` with `WithTag`/`WithoutTag`. Column names are plain strings. Claims use at scale ("hundreds of millions of orders daily") but publishes no numbers. MIT. — [go-sqlbuilder README](https://github.com/huandu/go-sqlbuilder)

#### bokwoon95/sq (typed table structs + row-mapper callbacks)
- "sq is a type-safe data mapper and query builder for Go"; "the act of mapping a column is the same as selecting it"; dialects SQLite, Postgres, MySQL, SQL Server, each with its own builder. Row mappers `func(*sq.Row) T` give compiler-checked result types. Go 1.19+ (docs say 1.18+ because "uses generics for data mapping"). Status: "sq is done for my use case (hence it may seem inactive, but it's just complete)." — [sq README](https://github.com/bokwoon95/sq), [sq docs](https://bokwoon.neocities.org/sq.html)
- Re-use: `sq.Expr()`/`sq.DialectExpr()` build reusable expressions with `{}` placeholders; custom components implement `SQLWriter`; `Queryf` queries have `Append()`; CTEs via `sq.NewCTE`/`sq.NewRecursiveCTE`; subqueries usable as fields, tables, IN and EXISTS; `PolicyTable` returns a `Predicate` automatically added to SELECT/UPDATE/DELETE. Compiled queries (`CompileFetch`, `CompileExec`) "amortize" build cost, can be "executed safely in parallel", and can be `Prepare(db)`'d into prepared statements. Enum values validated at runtime. Code generation of table structs is optional via `sqddl`. — [sq docs](https://bokwoon.neocities.org/sq.html)
- Executor interface: `type DB interface { QueryContext; ExecContext; PrepareContext }` (database/sql signatures). — [sq.go](https://github.com/bokwoon95/sq/blob/main/sq.go)

#### lqs/sqlingo (schema codegen + DSL)
- "Auto-generating DSL objects and model structs from the database"; MySQL stable, PostgreSQL and SQLite experimental; subqueries and expressions supported; "Many common errors could be detected at compile time"; no reusable-condition feature documented; no benchmarks; MIT. — [sqlingo README](https://github.com/lqs/sqlingo)

#### ent/ent (entity framework, schema-as-code)
- Raw/custom SQL only via feature flags: "The `sql/modifier` option lets add custom SQL modifiers to the builders and mutate the statements before they are executed" (e.g. `Modify(func(s *sql.Selector) { s.Select("SUM(LENGTH(name))") })`); `sql/execquery` "allows executing statements using the `ExecContext`/`QueryContext` methods of the underlying driver" but such statements "do not go through Ent, and may skip fundamental layers" (hooks, privacy, validators). — [ent feature flags](https://entgo.io/docs/feature-flags)
- Dialects: MySQL (5.6.35, 5.7.26, 8), MariaDB, PostgreSQL (10 through 17), CockroachDB (preview, Atlas), SQLite (via Atlas), Gremlin ("considered experimental"), TiDB (preview). — [ent dialects](https://entgo.io/docs/dialects)

#### go-gorm/gorm (+ gorm.io/gen and the 2025 generics API / `gorm` CLI)
- Generics API `gorm.G[T](db)` "available in v1.30.0 and later" (v1.30.0 published 2025-05-25 per GitHub release); claims improved "usability and type safety while reducing issues such as SQL pollution caused by reusing `gorm.DB` instances". A `gorm` CLI generates type-safe query code from an interface whose method comments hold SQL templates: "Simply define your query interface using Go's `interface` syntax, embedding SQL templates as comments"; placeholders `@@table`, `@@column`, `@id`, `@user.Name`; control flow `{{if}}`, `{{for}}`, `{{where}}`, `{{set}}`; `gorm gen -i ./examples/example.go -o query`. No quantitative performance claims. — [GORM generics docs](https://gorm.io/docs/the_generics_way.html), [gorm releases](https://github.com/go-gorm/gorm/releases/tag/v1.30.0)
- gorm.io/gen SQL annotations: `@@table` inserted at generation time; `@@<name>` table/column name from a string parameter escaped at runtime; `@<name>` binds a `?` parameter, slices expanded; `{{if/else}}`, `{{where}}`, `{{set}}`, `{{for}}`, `{{trim}}`; `where(...)` marks a method as a condition snippet passed to `Where`; return types derived from `gen.T`, `gen.M`, `gen.RowsAffected`, etc. "The page does not describe sharing SQL fragments across methods." — [gorm gen SQL annotation](https://gorm.io/gen/sql_annotation.html)
- go-gorm/cli repo description: "Type-safe GORM with SQL templates, model helpers, first-class associations" (created 2025-04-12). — [go-gorm/cli](https://github.com/go-gorm/cli)

#### uptrace/bun (SQL-first ORM/builder)
- "Lightweight, SQL-first Golang ORM for PostgreSQL, MySQL, MSSQL, SQLite, and Oracle"; "Performance optimized", built on `database/sql` with "minimal overhead"; no benchmarks on the README. BSD-2-Clause. — [bun README](https://github.com/uptrace/bun)
- Placeholders enabling fragment reuse: `?`, `?0`/`?1` positional, `bun.Ident` ("To quote SQL identifiers"), `bun.Safe` ("To disable quotation altogether"), `bun.In`, `?TableName`, `?TableAlias`, `?PKs`, `?TablePKs`, `?Columns`, `?TableColumns`; global named args via `db.WithNamedArg` ("db1 and db2 share the same *sql.DB, but have different named args"). — [bun placeholders](https://bun.uptrace.dev/guide/placeholders.html)
- Composition: `WhereGroup(" AND ", func(q *bun.SelectQuery) *bun.SelectQuery {...})`, `With("cte_name", subquery)`, `TableExpr("(?) AS alias", subquery)`, `ColumnExpr("(?) AS alias", subquery)`, raw queries `db.NewRaw("SELECT id, name FROM ? LIMIT ?", bun.Ident("users"), 100).Scan(ctx, &users)`. — [bun select docs](https://bun.uptrace.dev/guide/query-select.html)
- Reusable modifiers in source: "Apply calls each function in fns, passing the SelectQuery as an argument." `func (q *SelectQuery) Apply(fns ...func(*SelectQuery) *SelectQuery) *SelectQuery`. Executor: `IConn` "is a common interface for *sql.DB, *sql.Conn, and *sql.Tx" (QueryContext, ExecContext, QueryRowContext); `IDB` adds `Dialect()`; `NewDB(sqldb *sql.DB, dialect, opts...)` "wraps an existing *sql.DB with Bun". — [bun query_select.go / query_base.go / db.go](https://github.com/uptrace/bun)
- Design statement: "Bun's goal is to help you write idiomatic SQL, not to hide it behind awkward constructs." — [bun queries guide](https://bun.uptrace.dev/guide/queries.html)

#### wroge/sqlt (Go text/template SQL builder + struct mapper)
- "A Go Template-Based SQL Builder and Struct Mapper"; "uses Go's template engine to create a flexible, powerful, and type-safe SQL builder and struct mapper"; mapping via the separate `structscan` package with template actions like `{{ Scan.Int.To "Int" }}`; typed results via `sqlt.All[string, Data]`; topics MySQL/PostgreSQL/SQLite; no benchmark or caching notes on the README; 35 stars. MIT. — [sqlt README](https://github.com/wroge/sqlt)

#### VauntDev/tqla (template SQL with placeholder extraction)
- "Template Query Language Agnostic"; wraps `text/template`, replaces template variables with DB placeholders and collects args; "Tqla prevents sql injection by leveraging DB placeholders"; supports `{{ define }}`/`{{ template }}` re-use, `if`/`range`, `WithFuncMap`; option shown: `tqla.WithPlaceHolder(tqla.Dollar)`; "does not attempt to do any sql validation, this may change in the future." MIT. — [tqla README](https://github.com/VauntDev/tqla)

#### qustavo/dotsql (SQL-file loader)
- "is not an ORM, it is not a query builder"; queries identified by `-- name:` tags; `LoadFromFile`, `Merge`, `Exec`/`Query`/`QueryRow`/`Prepare`; templating via `WithData(map[string]any{...})` using text/template (`{{if .exclude_deleted}}`); no fragment mechanism; no typed scanning; GPL-2.0. — [dotsql README](https://github.com/qustavo/dotsql)

#### knadh/goyesql (SQL-file loader with struct-prepared statements)
- Parses files "with multiple named queries"; `-- name:` plus arbitrary `-- key: value` tags; `ScanToStruct` prepares `*sql.Stmt`/`*sqlx.Stmt`/`*sqlx.NamedStmt` fields via `query:"name"` tags; no fragments/includes; BSD-2-Clause; v2 import path. — [goyesql README](https://github.com/knadh/goyesql)

#### jmoiron/sqlx (database/sql extensions)
- Struct/map/slice scanning, `Get`/`Select`, `NamedQuery`/`NamedExec` with `:name` bindvars, batch `NamedExec` with slices, `BindDriver`; limitation: ambiguous column names in self-joins need `AS` aliases; MIT; last release listed on README 1.3.0 (GitHub API: v1.4.0, 2024-04-23). No query building or compile-time checking is claimed. — [sqlx README](https://github.com/jmoiron/sqlx)

#### jackc/pgx (driver; named args and statement cache)
- `NamedArgs` "will replace every '@' named placeholder with a '$' ordinal placeholder and construct the appropriate arguments"; `StrictNamedArgs` also checks that all and only the used names are supplied; `StructArgs` converts exported struct fields (using `db` tags) into named args. — [pgx named_args.go](https://github.com/jackc/pgx/blob/master/named_args.go)
- "pgx includes an automatic statement cache by default. Queries run through the normal [Conn.Query], [Conn.QueryRow], and [Conn.Exec] functions are automatically prepared on first execution and the prepared statement is reused on subsequent executions." Default mode `QueryExecModeCacheStatement`; PgBouncer 1.21+ with `max_prepared_statements` can use it; otherwise use `QueryExecModeExec`. — [pgx doc.go](https://github.com/jackc/pgx/blob/master/doc.go)

#### Interoperability with sqlc-generated code (executor interfaces, verbatim from source)
- sqlc `database/sql` output: `type DBTX interface { ExecContext(...)(sql.Result, error); PrepareContext(...)(*sql.Stmt, error); QueryContext(...)(*sql.Rows, error); QueryRowContext(...) *sql.Row }`. sqlc pgx output: `type DBTX interface { Exec(context.Context, string, ...interface{}) (pgconn.CommandTag, error); Query(...)(pgx.Rows, error); QueryRow(...) pgx.Row }` plus optional `CopyFrom`/`SendBatch`. — [sqlc-gen-go stdlib template](https://github.com/sqlc-dev/sqlc-gen-go/blob/main/internal/templates/stdlib/dbCode.tmpl), [pgx template](https://github.com/sqlc-dev/sqlc-gen-go/blob/main/internal/templates/pgx/dbCode.tmpl)
- Jet `qrm.DB` (Exec/ExecContext/Query/QueryContext on `*sql.Rows`), sq `DB` (QueryContext/ExecContext/PrepareContext), squirrel `StdSqlCtx`, Bun `IConn` are all satisfied by `*sql.DB`/`*sql.Tx`; Bob requires wrapping via `bob.NewDB(*sql.DB)` because its `QueryContext` returns `scan.Rows`. (Sources as cited in each library section above.)
- pggen depends on pgx v4 (`github.com/jackc/pgx/v4 v4.18.3`), while sqlc's pgx templates import `pgconn`/`pgx` from the configured major version. — [pggen go.mod](https://github.com/jschaf/pggen/blob/main/go.mod)

### Inferences
- Bob's query generation is the only fetched tool that (a) parses hand-written `.sql` query files with annotations, (b) type-checks against a schema and (c) emits objects that can be extended with typed mods (`With(sm.Where(...))`). Its re-use direction is "generated static query + runtime additions", not "shared named fragments reused across several static queries"; nothing on the docs page supports `-- include`-style fragments, so a shared column list or predicate still has to be duplicated in each `.sql` query (or expressed as a Bob builder mod in Go).
- Bob's `go.mod` shows the same PostgreSQL parser family that sqlc uses (`pg_query_go`, i.e. libpg_query) plus ANTLR grammars via `stephenafamo/sqlparser`; the v0.43.0 "driver image" setting for `bobgen-sql` plus the `testcontainers` dependency suggest MySQL/PostgreSQL schema parsing in `bobgen-sql` runs a containerized database rather than a pure-Go parser (inference; the docs page does not say).
- Executor-level interop with sqlc is easy for every `database/sql`-based builder (same `*sql.DB`, same `*sql.Tx` in one transaction), and for pure string builders (squirrel, go-sqlbuilder, sqlt, tqla, sq's `ToSQL`) with sqlc's pgx `DBTX` by passing `(sql, args)` to the same `pgxpool.Pool`. Model-level interop is weak: every generator (sqlc, Bob, jet, SQLBoiler, gorm gen, ent, pggen) emits its own structs, so combining two generators means two model sets. Bob's `result_type_one/all` annotations accept package-qualified types and skip generation when "manually set", which is a plausible (UNVERIFIED in practice) bridge for mapping Bob-generated queries onto sqlc-generated model structs.
- pggen is effectively a sqlc contemporary rather than a successor: single-maintainer, pgx v4, last tag January 2024, last commit March 2025, no composition features; its one design difference (type inference by running queries on a live Postgres) is now also on sqlc's own 2026 roadmap ("database-only analysis").
- For a new library, the designs worth borrowing are: Bob's "generated query is also a mod" (static query as a base object), sq's compiled/prepared queries with default parameters and `PolicyTable` auto-predicates (addresses the HN complaint about per-tenant filters), gorm gen's `where(...)` condition snippets generated from annotated templates, Bun's `?TableColumns`/`?PKs` model-derived placeholders and `Apply(fns...)`, go-sqlbuilder's shared `WhereClause` between SELECT and UPDATE, and Bob v0.49.0's reflection-free per-table scan mapper for scanning cost.

### Gaps
- Open-issue *trend* over time is not available from a single API snapshot; only current counts (issues plus PRs) were captured.
- goqu's executor interface (`exec.DbExecutor`) and the exact `goqu.New(dialect, db)` signature were not fetched (code search returned nothing); GORM's and ent's "wrap an existing *sql.DB" entry points and sqlx's `NewDb` were not fetched in this pass and are therefore UNVERIFIED here.
- Bob's generated `.bob_test.go` tests: the docs say to run them but do not state whether a live database is needed; the CHANGELOG (v0.35.0 era) mentions tests "that required a database connection" depending on a user-provided `testDB`, which suggests yes but was not confirmed on the docs page.
- Whether Bob generated queries can be embedded as subqueries/CTEs in builder queries is not documented on the queries page (only `With()` mods are).
- pggen: no explicit archived/maintenance statement exists; status is inferred from activity dates only.
- sqlingo, sqlt, tqla, relica: no independent performance data found.
- gnorm, sqlf, go-rel/rel, ksql, scany, superbasic: only repository metadata was fetched, not feature documentation.

## Key Question 2: Which tools keep plain SQL text (sqlc's appeal) while allowing fragments, and which require a DSL?

### Takeaway
Tools that keep SQL text and add fragment sharing do so only through text templating with no static checking (sqlt, tqla, dotsql `WithData`, gorm gen annotations); tools with static checking of composed queries do so through Go DSLs that replace SQL text (jet, Bob builder, sq, sqlingo); Bob's query generation is the only hybrid, keeping SQL text for the base query and using the DSL for extensions.

### Cited Findings
- Keep SQL text, no fragments, no static checks: sqlx (`NamedQuery`, `:name` bindvars) — [sqlx](https://github.com/jmoiron/sqlx); pgx `NamedArgs`/`StrictNamedArgs`/`StructArgs` — [pgx](https://github.com/jackc/pgx/blob/master/named_args.go); dotsql `-- name:` files, templating via `WithData` with text/template — [dotsql](https://github.com/qustavo/dotsql); goyesql `-- name:` plus arbitrary tags, "does not mention query fragments, includes, or reusable SQL snippets" — [goyesql](https://github.com/knadh/goyesql).
- Keep SQL text, fragments via Go templates, no validation: tqla supports `{{ define "name" }}`/`{{ template "name" . }}` and "does not attempt to do any sql validation" — [tqla](https://github.com/VauntDev/tqla); sqlt uses "Go's template engine" with typed result mapping via `structscan` — [sqlt](https://github.com/wroge/sqlt); gorm gen SQL annotations with `{{where}}`/`{{if}}` and `where(...)` condition snippets, generated from interface comments, but "does not describe sharing SQL fragments across methods" — [gorm gen](https://gorm.io/gen/sql_annotation.html).
- SQL text for the base query, DSL for extension, static checks on the base: Bob query generation ("similar to sqlc") whose generated `orm.ModQuery` "can also be used as a QueryMod" and extended via `With()` — [Bob docs](https://bob.stephenafamo.com/docs/code-generation/queries). Static-only SQL text with no extension: sqlc, pggen ("one generated method per named query"; no composition) — [pggen](https://github.com/jschaf/pggen), xo/dbtpl query mode — [dbtpl](https://github.com/xo/dbtpl).
- Replace SQL text with a Go DSL, with compile-time typing of columns/expressions: jet (generated typed columns; "string columns compare only with string expressions"; raw SQL only "With the loss of all Jet benefits") — [jet](https://github.com/go-jet/jet), [jet FAQ](https://github.com/go-jet/jet/wiki/FAQ); sq (typed table structs, `func(*sq.Row) T` mappers, `sq.Expr()` raw escape) — [sq docs](https://bokwoon.neocities.org/sq.html); sqlingo ("Many common errors could be detected at compile time") — [sqlingo](https://github.com/lqs/sqlingo); Bob builder (dialect-specific mods; unsupported mods fail at compile time; `psql.Raw()` for fragments) — [Bob building queries](https://bob.stephenafamo.com/docs/query-builder/building-queries).
- Replace SQL text with a DSL whose column names are strings (runtime-only checks): squirrel ("composable parts") — [squirrel](https://github.com/Masterminds/squirrel); goqu (`goqu.Ex` maps, `With` CTEs) — [goqu](https://github.com/doug-martin/goqu); go-sqlbuilder (string columns, `Clone()`, shared `WhereClause`, `SQL(...)` fragments) — [go-sqlbuilder](https://github.com/huandu/go-sqlbuilder); Bun (SQL-ish strings with `?TableColumns` placeholders and `Apply`) — [bun placeholders](https://bun.uptrace.dev/guide/placeholders.html); relica — [relica](https://github.com/coregx/relica).
- ORMs where raw SQL is an escape hatch: ent `sql/modifier` and `sql/execquery` flags (raw statements "may skip fundamental layers") — [ent](https://entgo.io/docs/feature-flags); GORM generics API plus template-annotated interfaces — [GORM](https://gorm.io/docs/the_generics_way.html).
- sqlc-plugin route that keeps SQL text: MrEhbr/sqlc-gen-go generates `Query[T]` values and lets hand-written `NewStatement(sql, args...)` queries share the executor, but is "not compatible with standard sqlc" and needs Go 1.27+ — [MrEhbr/sqlc-gen-go](https://github.com/MrEhbr/sqlc-gen-go).

### Inferences
- The design space has an empty cell: "SQL text with named, statically type-checked fragments (column lists, predicates, CTE bodies) reused across several `.sql` queries". Template engines fill the "fragments" half without checking; sqlc/pggen/dbtpl fill the "checked SQL text" half without fragments; Bob bridges only at the Go level after generation.
- gorm gen's annotated-interface approach is the closest precedent for "fragment-like" constructs in SQL text (`where(...)` snippets, `{{where}}` trimming), but its checking is template-level, not schema-level.

### Gaps
- No fetched documentation for any tool describes a `-- include`/`{{template}}`-style fragment that is expanded *before* schema-aware analysis; if such a tool exists it was not found by searches for "composable SQL fragments Go sqlc-like" (search returned only the sqlc-gen-go fork and builders).

- A new library targeting sqlc-level performance should aim for the sqlc/pgx envelope (about 8 allocs per Insert/Update, 18 to 19 per single-row Read, roughly 5 to 6 allocs per scanned row in ReadSlice) and keep per-call SQL assembly under a few µs, e.g. by caching assembled SQL per fragment combination so repeated executions behave like prepared statements under pgx's default statement cache (capacity 512).

## Key Question 4: What the authors of Bob, jet and sq say about sqlc's lack of composability

### Takeaway
Only Bob's author addresses sqlc explicitly: Bob's query generation is described as "similar to sqlc" and positioned as extending type safety "to hand-crafted SQL queries", with the stated advantage that a generated query "can be used as a base" for more mods. Jet's and sq's documentation do not mention sqlc at all; the composability critique of sqlc comes from users (Hacker News, sqlc discussion #364), not from these authors.

### Cited Findings
- Bob README: "Code generation of Queries similar to sqlc"; Layer 4 heading "similar to sqlc"; "I believe this is the final peice of the puzzle, and extends the type-safety to hand-crafted SQL queries." - Bob docs (Queries): "This is similar to sqlc." and "The generated query is a `orm.ModQuery` object, which can also be used as a QueryMod. - Bob CHANGELOG v0.46.0 (2026-06-11): "`With()` on generated queries as a more ergonomic method to add mods on top of generated queries (thanks @daddz)". — [Bob CHANGELOG](https://github.com/stephenafamo/bob/blob/main/CHANGELOG.md)
- Jet README: "compares Jet only with ORM libraries. It does not mention sqlc or other code-generation tools." ## Key Question 5: Using sqlc for the static 90 percent plus a builder for dynamic queries; reported friction

### Takeaway
"sqlc for static queries plus Squirrel (or jet) for dynamic ones" is the pattern recommended by 2025 to 2026 comparison articles and practiced by commenters in sqlc discussion #364, but users report two ways of handling SQL in one codebase, duplicated near-identical queries, hand-written mapping code, and cognitive overhead of knowing which tool to use; sqlc's maintainer said in 2020 that dynamic queries would not be a priority, and the 2026 roadmap still contains no such item.

### Inferences
- The friction reported is structural, not tooling-specific: (1) two query-authoring models (SQL text vs Go DSL), (2) duplicated model/row structs because sqlc's generated structs are not reused by the builder's scanner and vice versa, (3) duplicated near-identical SQL for variants sqlc cannot parametrize (`FOR UPDATE`, ORDER BY column, optional predicates), (4) dynamic-filter workarounds inside sqlc (`CASE WHEN`, `NOT @has_x OR ...`) that degrade plans or indexes.
- Because sqlc's Go API/engine plan (roadmap #4204) exposes parse/analyze stages, a new library could reuse sqlc's analysis for statically checked fragments and emit composable query values (as the MrEhbr fork does at the plugin level) instead of running a second analyzer.
